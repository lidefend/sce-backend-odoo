# Demo 演示数据质量标准 v1

> 状态：标准制定。本次只确立验收口径，不修改数据、不重新验证实库。
> 分支/基线：`main` @ `c937f2ee60162463f4914e148baac20b0a1406db`（首版预览发布后）。
> 归属：P4 demo delivery 验收口径；产品面缺口按 P0/P1/P3 另行登记与迭代。
> 上游：`docs/demo/demo_baseline_readiness_v1.md`（G0–G6 基线就绪排查）。

## 0. 判定原则

Demo 数据合格的标准，是用户能看懂业务、以真实角色完成操作，并且结果可追溯、可核验。
记录存在、页面能打开、CI 通过，都不能单独证明数据合格。

本文把 `demo_baseline_readiness_v1.md` 的“基础数据齐全”收紧为“业务事实自洽、角色可办理、
用户能理解、证据可复核”。本文件只制定标准；实库核对、角色定向操作与页面消费验证在后续
阶段按标准执行并留证，不在本次范围内。

## 1. 统一验收对象

按“演示案例”验收，每个案例必须声明：

- 展示的产品能力及成熟度：标准或预览。
- 项目、公司、业务期间和关联单据。
- 参与角色、数据范围和具体操作。
- 起点、操作步骤、预期结果、异常分支。
- 数据版本、运行环境、契约版本及验证证据。

产品能力发布状态与角色办理权限分别验收。能力已发布，不代表所有角色都有入口或操作权；
预览能力也不能降低数据真实性、金额正确性和权限要求。

## 2. 数据质量硬标准

| 维度 | 合格要求 | 不合格情形 |
|---|---|---|
| 基础完整性 | 场景需要的公司、组织、人员、客商、账户、税率、单位、项目及资金前置齐全 | 有单据但缺负责人、相对方、付款依据，下一步无法办理 |
| 业务真实性 | 名称、内容、数量和金额符合明确的业务背景；演示主案例具有可解释的规模 | “测试项目”“合同001”、无意义重复记录、随意拼接金额 |
| 关联一致性 | 项目—合同—结算—付款—执行—台账可逐级追溯，公司、相对方及业务方向符合契约 | 关联到其他项目，收支方向混用，孤儿记录 |
| 金额一致性 | 数量、单价、税额、含税总额及累计金额按契约核对；精度遵循币种和舍入规则 | 含税与未税混算；将资金上限当余额；从不同口径直接相减 |
| 生命周期一致性 | 每个状态由正式动作产生，前后置关系符合产品契约，有对应历史 | 直接写终态、伪造审批、未经解释的草稿合同与已付款链 |
| 时间一致性 | 业务日期顺序合理，当前任务在声明的业务时钟下有效；历史案例明确标识 | 已过期基线支撑当前办理；历史完成事项伪装成今日待办 |
| 角色与权限 | 真实角色具备已声明的读、建、改、提交、审批或执行权限；越权负例被拒绝 | 用管理员跑通代替业务角色；有读取权就推定有办理权 |
| 展示可理解性 | 列表与详情能识别同一业务，字段标签、单位、状态和引导与契约一致 | 技术标识占据主要展示面；文案把草稿称为已签署 |
| 汇总可核对性 | 工作台、驾驶舱、台账汇总来自真实业务事实，按同一范围可追溯 | 手工造指标、看板与明细不一致、未声明的更新滞后 |
| 体验可持续性 | 体验记录有明确归属；重复执行不重复造数；清理不破坏展示基线 | 用户一操作就毁掉主案例；全库重建代替体验清理 |
| 证据完整性 | 绑定环境、部署版本、账号、对象、时间、命令及原始结果 | 只有口头结论、源码截图或无原始日志的通过摘要 |

历史编号含 2025、小额记录、空态本身不自动构成缺陷。必须看其业务用途：历史编号可以保留；
小额风险测试应与主展示案例分开；空态必须是有意设计且有解释的状态。

## 3. 首版至少准备三类案例

| 案例类型 | 必须证明的效果 |
|---|---|
| 完整历史案例 | 用户能从项目追溯到业务结果，金额、状态、时间和关联全部自洽 |
| 可办理案例 | 每个承担办理职责的演示角色至少有一项真实任务，完成操作后能看到结果和下一处理者 |
| 异常引导案例 | 覆盖前置缺失、无权限、业务校验失败等已发布机制；错误原因清晰，修复路径来自契约 |

只读管理角色应有可核对的概览和授权下钻，不强行制造办理任务。同一单据不能同时冒充“已完成历史”
和“待审批任务”。

## 4. 分阶段放行

| 阶段 | 放行要求 |
|---|---|
| 数据基线合格 | 必要基础数据齐全，关联、金额、状态、时间校验通过 |
| 预览演示合格 | 基线合格；前后端及角色面契约对齐；展示事实准确；未开放的交互明确说明 |
| 交互演示合格 | 在预览基础上，真实角色完成声明的操作、接力和结果回读，体验清理验证通过 |

预览阶段允许展示和交互继续完善，不允许金额错误、越权、伪造状态或虚假能力说明。异常数据可作为
明确标识的诊断案例，不能充当成功主案例。

## 5. 验收门槛与验证方式

首版声明范围内必须满足：

- 必要字段、关联和业务前置完整率 100%。
- 金额、生命周期、时间及汇总核对通过率 100%。
- 声明的角色／对象／动作组合验证覆盖率 100%。
- 越权读取、越权操作、伪造审批、直接造派生指标 0 项。
- 主演示路径阻断问题 0 项。
- 每项通过结论均有可追溯证据；缺证据记为“未验证”。

验证顺序为：契约声明检查 → 实库只读核对 → 真实角色定向操作 → 页面消费验证。复用输入和环境
未变化的有效证据，只补缺失或受影响的集合；不能每次重跑全矩阵，也不能把“曾经验证过”当作永久
有效。

## 6. 当前 s69 案例按这套标准的判定

依据现有交接计划
（`sce-backend-odoo-local-env/docs/demo/demo_usage_foundation_plan_v1.md:146`），目前不能认定为
合格的完整主案例：

| 已知情况 | 判定与整改要求 |
|---|---|
| 合同基础额 240000、含税额 271200，结算 240000、付款 120000 | 不能直接判错，但结算税口径及可付金额依据尚未闭合，禁止推算“剩余应付” |
| 合同为 draft，结算 approve、付款 done | 生命周期关系待契约解释或修复；仅修改文案不足以达到完整主案例标准 |
| 资金基线 1000000、期间至 2026-12-31 | 不能称为可用余额；当前办理还需核对有效性及占用口径 |
| 部分角色可读付款申请 | 只能证明已记录的读取范围，不能证明创建、提交、审批、付款执行权限 |
| 历史付款已完成 | 可用于结果展示，不能代替角色当前可办理任务 |
| S5 仅保留摘要，原始日志不可得 | 属于证据缺口，不能沿用为完整验收通过凭证 |

这套标准延续仓库已有的基线就绪要求（`docs/demo/demo_baseline_readiness_v1.md`），进一步把
“基础数据齐全”收紧为“业务事实自洽、角色可办理、用户能理解、证据可复核”。
