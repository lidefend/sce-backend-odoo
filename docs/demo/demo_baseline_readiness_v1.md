# Demo 基线就绪排查 v1（G0–G6）

> 状态：只读排查与计划输入，不落库、不改产品代码。
> 分支/基线：`feature/demo-iteration-line-20261020` @ `13b0395db4da63147b3f9c311a4bb5d060dc6a4e`
> 归属：P4 demo delivery；产品面缺口按 P0/P1/P3 另行登记与迭代。

## 1. 结论

Demo 数据必须按“基础数据 → 项目基线 → 交易数据 → 证据”的顺序准备，不能先造合同、结算、
付款，再回头补客户、供应商、科目、审批岗位和资金基线。

当前问题不是“表里完全没有数据”，而是：

- 基础数据的公司/租户/角色作用域没有和体验登录身份对齐；
- 部分金额、日期和状态不具备真实业务连续性；
- 现有 `demo.verify` 主要是 SQL 存在性断言，不是业务链、审批和角色可见性验收；
- 体验用户产生的数据与 demo 基线数据的清理边界需要显式分开。

本次只读统计正式入口验收表：90 行入口证据中有 65 行记录了空态/0 渲染；其中 27 行明确是
“数据归属公司 1、受测公司作用域排除”。这不全是缺陷，配置/投影入口可以合法为空，但它说明
demo 数据与验收身份没有对齐。

## 2. 数据分类

| 类别 | 定义 | 处理原则 |
|---|---|---|
| 硬前置 | 缺失时业务动作直接失败，或单据无法成立 | 必须先到位，并纳入就绪门禁 |
| 条件前置 | 当前场景需要时才必须存在 | 按场景声明，不要求全局齐全 |
| 配置 | 决定流程、编号、菜单、字段和权限的声明 | 配置一次，按版本审计，不按记录重复造 |
| 项目基线 | 项目启动后、交易发生前必须建立的事实 | 每个项目单独建立并回读 |
| 交易事实 | 合同、结算、付款、付款登记、台账等业务结果 | 只能由正式动作产生，不能直接写终态 |
| 派生投影 | 工作台、驾驶舱、成本台账、经营指标、汇总报表 | 由事实计算，禁止直接 seed |

## 3. 基线就绪门槛

### G0 租户与公司

必须先到位：

- 公司法定名称、统一社会信用代码、地址、联系方式；
- 公司本位币、会计年度、科目表、日记账、税种/税率；
- 数据空间、公司作用域、精确数据库/租户/dbfilter；
- 平台管理员与业务管理员的职责分离。

缺失的直接后果：单据公司/币种为空，跨公司记录不可见，合同、结算、付款金额口径不一致。

当前证据：`demo_company_identity`、`company_currency_cny` 种子步骤；`config/ops/daily_runtime_database_duties.v1.json`
声明 demo duty；`scripts/demo/tenant_lifecycle.sh` 校验隔离租户身份。

归属：P0 平台机制、P2 客户基础配置、P4 demo 租户载体。

### G1 组织与身份

必须先到位：

- 部门树、岗位、员工档案；
- 业务用户、角色/能力组、项目成员；
- 审批岗位与审批范围；
- 项目负责人、成本负责人、资料负责人。

缺失的直接后果：审批人、负责人和可见范围缺失；付款申请、合同事件、材料验收、分包等
模型会出现“有单据但无人可办”的状态。

当前证据：`data/base/12_departments.xml`、`13_departments_tree.xml`、`14_jobs.xml`、
`data/demo/sc_demo_employees.xml`、`sc_demo_organization_bindings.xml`。其中部门文件明确说明
“部门是多项业务事实的必填项”，不能靠绕过守卫满足。

重要边界：`sc_demo_organization_bindings.xml` 明确 `manager_id` 只用于组织展示与分组，
不构成审批路由。若产品期望“部门负责人审批”，必须在 P1 审批机制中显式实现或明确告知用户
审批岗位由审批策略配置，不能在 demo 里用组织负责人冒充审批人。

归属：P2 客户组织数据、P3 角色/导航配置、P1 审批范围声明。

### G2 业务主数据

必须先到位：

- 客户/业主、供应商/分包商：名称、类型、税号、联系人、银行账户、付款条件；
- 客商分类、供应商类型、业务类别；
- 税种、税率、计量单位、付款条件；
- 材料目录与材料价格；
- 项目类型、项目类别、成本项、定额/专业/章节/子目字典；
- 成本科目树、WBS/BOQ 模板、合同模板、资料类型。

缺失的直接后果：合同/结算/付款选不到相对方；金额、税率、科目、材料价格不完整；表单看似
可保存，但后续审批和台账无法闭环。

当前证据：`data/base/00_dictionary.xml`、`05_partner_categories.xml`、`dictionary_demo.xml`、
`cost_demo.xml`、`10_partners.xml`、`15_seed_partners.xml`；`sc.business.category` 的模板绑定；
`sc.material.catalog` 与 `sc.material.price` 模型约束。

归属：P1 行业主数据模型、P2 客户主数据值、P3 业务类别/表单配置。

### G3 治理与运行时配置

必须先到位：

- 审批策略、审批步骤、审批范围；
- 单据编号规则；
- 菜单、动作、场景、能力发布；
- 列表/表单/搜索/字段策略；
- 数据权限与记录规则。

缺失的直接后果：提交自动通过或根本没有审批实例；入口不可见；字段不可编辑；角色看到
不该看的数据。

当前证据：`sc.approval.policy` 内置用户可见模板，覆盖付款/收款、合同、结算、采购等；
`sc.product.numbering.rule` 继承 `ir.sequence`；`sc.approval.policy.runtime_state` 区分
`tier_validation`、`document_state`、`policy_only`。

归属：P0 平台契约与运行时、P1 行业审批模板、P3 低代码配置。

### G4 项目基线

每个项目在交易前必须先到位：

- 项目名称、项目编号、公司、经营方式、项目类型/类别；
- 业主、项目经理、成本负责人、资料负责人、项目地点、日期；
- 项目成员与项目数据范围；
- 资金承载开关与生效的资金基线；
- 预算/目标成本、BOQ 版本与清单、WBS/LBS/标段/执行范围；
- 合同或采购订单等结算依据。

缺失的直接后果：付款申请提交时被资金承载、结算状态、采购来源、合同依据等硬前置阻断；
项目看板和成本分析没有稳定口径。

当前证据：`project.project` 要求阶段、经营方式、项目编号唯一；`payment.request` 提交前要求
项目资金就绪、资金基线有效、申请金额大于 0、存在合同/结算依据；`sc.settlement.order`
审批时对外结算要求采购订单来源；`project.funding.baseline` 要求标准化版本、完整控制期、
公司/币种、资金上限大于 0、至少一条计划明细且明细合计等于上限。

归属：P1 项目/资金/合同模型、P2 项目基线数据、P4 demo 种子。

### G5 交易事实

按主链顺序产生：

1. 合同（草稿 → 生效/执行中 → 关闭）；
2. 采购订单/材料验收/入库；
3. 进度计量/成本归集；
4. 结算单（草稿 → 提交 → 批准 → 完成）；
5. 付款申请（草稿 → 提交 → 审批中 → 已批准 → 已完成）；
6. 付款登记（草稿 → 已确认 → 已付款）；
7. 付款台账（有效 → 冲销）。

这些状态只能由正式业务动作产生。Demo 种子可以准备草稿和关联，但不能直接写终态，也不能
伪造审批历史。

当前证据：`S10`、`S20`、`S30` 场景；`docs/demo/r1-02-realistic-core-chain.md` 已明确
“不落库、不伪造审批终态”；`payment.request`/`sc.settlement.order`/`payment.execution`
均有状态守卫。

归属：P1 业务模型、P4 demo 场景种子。

### G6 证据与回读

必须先到位：

- 角色工作台待办、审批待办、风险提醒；
- 审计日志、审批历史、付款台账；
- 项目驾驶舱、成本/资金/经营指标；
- 角色可见性与负例（无权限角色不应看到）。

这些应以事实为源派生。`sc.workbench.item`、`sc.dashboard.cockpit.fact`、
`sc.operating.metrics.project`、成本/资金汇总和盈亏分析不应由 demo 直接造数；否则会出现
“投影说一套、事实说另一套”的双口径。

归属：P1 事实投影、P3 场景/工作台配置、P4 验收证据。

## 4. 必须造 vs 必须派生

| 必须准备/配置 | 必须派生，禁止直接 seed |
|---|---|
| 公司、币种、会计年度、科目、税、日记账 | 工作台待办、审批待办、最近访问 |
| 部门、岗位、员工、用户、角色、项目成员 | 项目驾驶舱指标、经营指标 |
| 客户、供应商、联系人、银行账户、付款条件 | 成本台账（如由事实归集） |
| 客商分类、供应商类型、业务类别 | 资金/成本/发票/工资汇总 |
| 材料目录、材料价格、计量单位 | 盈亏分析、公司经营汇总 |
| 项目字典、成本科目、WBS/BOQ 模板 | 风险信号（如由风险事实计算） |
| 审批策略、审批步骤、编号规则 | 报表快照（除非是明确的历史归档） |
| 项目、资金基线、预算、BOQ、WBS、合同/采购 | 审批历史（必须由真实审批动作产生） |

条件数据：附件、质量/安全标准、劳务/设备价格、投标文件类型、资料细类，按当前演示场景
需要时再准备，不要求全局齐全。

## 5. 业务动作依赖矩阵

| 业务动作 | 必须先有 | 系统守卫/证据 | 归属 |
|---|---|---|---|
| 新建项目 | 公司、币种、阶段、项目经理、业主 | `project.project` 必填与编号唯一 | P1/P2 |
| 提交合同 | 项目、相对方、币种、税率、编号、审批策略 | 合同状态机、审批实例 | P1/P3 |
| 提交结算 | 项目、相对方、明细、合同；外结算还需采购订单 | `_check_business_anchor_or_raise`、采购来源校验 | P1 |
| 提交付款 | 项目资金就绪、生效资金基线、合同/结算已批准、相对方、账户、审批策略 | `P0_PAYMENT_FUNDING_*`、`P0_PAYMENT_SETTLEMENT_NOT_READY` | P1 |
| 生成付款登记 | 已批准付款申请、收款账户完整、付款执行策略 | `action_create_payment_execution` 守卫 | P1 |
| 查看工作台 | 角色、项目成员、审批实例、菜单/场景/能力 | `my.work.summary` 聚合 | P0/P3 |
| 查看经营指标 | 交易事实 + 投影服务 | `sc.operating.metrics.project` | P1 |

## 6. 当前已发现缺口

1. **作用域未对齐**：27 行入口证据明确显示数据归属公司 1、受测公司作用域排除；65 行记录
   空态/0 渲染。先修 demo 公司/角色/数据作用域，再谈补数。
2. **真实性与时效不足**：showroom 种子仍有结算单价 `100.0`、付款金额 `50.0`；部分场景固定
   2025 年日期，而当前系统日期已到 2026 年。金额和日期需要按业务日历重新锚定。
3. **验证口径不足**：`make demo.verify` 主要是 SQL 存在性；不能证明审批、角色可见性、跨记录
   金额/日期自洽和用户下一步。
4. **种子步骤名不等于数据到位**：`dictionary`、`project_skeleton` 等步骤目前只是证据标记，
   实际数据来自 XML；就绪判断必须回读真实模型，不能看 step 名称。
5. **组织负责人不是审批路由**：`manager_id` 只用于展示/分组；审批需由 `sc.approval.policy`
   与审批范围显式声明。若产品要“部门负责人审批”，属于 P1 机制缺口。
6. **审批动作提示静态**：`payment.request.available_actions` 把 approve/reject 的岗位提示
   固定为管理层，而默认付款审批是四级（财务经办 → 项目负责人 → 财务审核 → 管理层）。
   实际 `allowed` 仍按 `can_review` 判断，但交接提示会误导中间级审批人。
7. **项目最小创建与下游硬前置之间存在空档**：项目可以只填名称和经理创建，但付款提交还要求
   资金基线、合同/结算、账户等；产品面应提供“办理前检查”，不能等用户提交时才报错。
8. **体验数据与 demo 基线的清理边界必须显式化**：体验用户产生的记录、编辑、附件、审批、
   消息和会话，不能通过“全库重建 demo”来清理；demo 基线也不能被体验重置误删。

## 7. 建议的基线就绪契约

建议在 P1/P3 产品面提供一个后端就绪投影（名称可后续拍板），例如
`baseline.readiness`，按公司/项目/角色返回：

```json
{
  "gate": "G4",
  "status": "ready|partial|blocked|not_applicable",
  "required": ["funding_baseline", "contract", "partner_account"],
  "present": ["funding_baseline", "contract"],
  "missing": ["partner_account"],
  "authority": "project.funding.baseline/payment.request",
  "repair_hint": "补充收款账户开户行与账号",
  "owner_layer": "P1"
}
```

前端只消费该契约，展示“开始使用前检查”和修复入口；demo 种子、工作台和后台管理页共用同一
就绪结论，禁止前端自行推导。

## 8. 基线验收判据

- G0–G4 对目标公司/目标项目全部 `ready`，且 `missing=[]`；
- 同一公司、同一角色、同一项目作用域下可读；
- 业务动作不使用 admin/superuser；
- 审批实例、资金基线、合同/结算依据有真实回读；
- 派生投影由事实产生，不出现直接 seed 的工作台/驾驶舱/汇总记录；
- 体验重置前后，demo 基线指纹不变；体验用户产生的增量被清理。
