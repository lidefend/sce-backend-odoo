## 1. 唯一目标

建立一套**可被真实用户直接使用、可持续演化、可由 API 和浏览器重复验收**的 demo 基础数据：

1. 用户登录后，身份、公司、角色、项目范围正确；
2. 第一个业务动作所需的组织、主数据、流程配置和项目基线已经到位；
3. 前端表单里能选到可用数据，而不是只在数据库里存在；
4. 业务动作通过公开 intent/action 推进，审批人真实存在且能办理；
5. 系统每天推进的是 demo 事实和角色待办；体验用户操作产生的增量另行重置；
6. 任何缺口立即登记，按 P0/P1/P2/P3/P4 归属处理，不在 demo 层写死产品语义。

## 2. 用户使用主线

本计划统一按以下用户路径组织，不按表名或 seed 步骤名组织：

```text
登录
→ system.init / role_surface / default_route
→ 我的工作：今天要办什么
→ 新建或打开项目
→ 选择业主、供应商、税、付款条件、材料、成本项
→ 建立资金基线、预算、BOQ/WBS
→ 创建合同/采购依据
→ 提交合同
→ 审批人收到真实待办并办理
→ 产生结算、付款申请、付款登记和台账事实
→ 工作台与驾驶舱从事实派生
→ 每日定时任务推进 demo 叙事
→ 体验用户操作增量被单独清理
```

每一步都必须回答三个问题：

- 用户此时看到什么；
- 用户下一步能点什么；
- 系统用什么后端事实证明这一步成立。

## 3. 基础数据分层

| 层级 | 必须先行到位的数据 | 用户可感知结果 | 责任层 |
|---|---|---|---|
| U0 身份与范围 | 公司、公司访问、部门、岗位、员工、用户、角色、项目成员、数据规则 | 登录后角色正确，只看到职责内的公司和项目 | P0/P2/P3，P4 数据载体 |
| U1 业务主数据 | 业主、客户、供应商、分包商、联系人、银行账户、税种税率、付款条件、计量单位 | 新建合同、结算、付款时能选到完整有效的相对方和口径 | P1/P2，P4 数据载体 |
| U2 项目参考数据 | 项目类型/类别、成本项、合同类型、资料类型、材料目录、价格、成本科目 | 项目、预算、BOQ、合同表单可直接使用，无空选项 | P1/P2，P4 数据载体 |
| U3 流程与权限配置 | 审批策略、审批步骤、审批范围、编号规则、菜单、动作、能力、数据权限 | 提交后生成真实审批，办理人可见且能完成；无权用户被拒绝 | P0/P1/P3，P4 只读消费 |
| U4 项目启动基线 | 项目主档、业主、项目经理/成本/资料负责人、资金基线、预算、BOQ/WBS、合同或采购依据 | 项目可启动，付款提交前能看到并满足硬前置 | P1/P2，P4 数据载体 |
| U5 日常事实 | 任务、施工日志、到货/验收、进度、风险、收付款、台账 | 每个角色每天有真实事项，首页不是模板或静态样例 | P1，P4 场景驱动 |
| U6 派生结果 | 我的工作、风险提醒、驾驶舱、成本/资金/经营指标 | 展示值与业务事实一致，禁止直接 seed | P1/P3，P4 验收 |

### 3.1 必须造 vs 必须派生

必须作为基础数据准备：

- 公司、币种、会计年度、科目、税、日记账；
- 部门、岗位、员工、用户、角色、项目成员；
- 业主、客户、供应商、联系人、银行账户、付款条件；
- 计量单位、材料目录与价格、项目字典、成本科目、WBS/BOQ 模板；
- 审批策略、审批人/范围、编号规则、菜单/动作/能力发布、数据权限；
- 项目、资金基线、预算、BOQ/WBS、合同或采购依据。

必须由事实派生，禁止直接 seed 成“终态数据”：

- 我的工作待办与风险提醒；
- 驾驶舱指标、成本台账、资金/经营汇总；
- 审批历史与审批意见；
- 任何绕过公开动作写出的业务终态。

## 5. 分批次执行单

### F1：使用基础数据契约与缺口审计

- 目标：把用户路径变成可审计的基础数据清单。
- 新增/更新：`docs/demo/demo_usage_foundation_manifest_v1.json`（后续实现）、只读审计脚本/测试、
  `docs/demo/product_gap_registry_v1.md`。
- 每个 requirement 至少声明：`key`、用户动作、硬/条件前置、模型/公开读取入口、
  作用域、责任层、修复提示、验收方法。
- 先审计，不补数；发现产品缺口立即登记，不在 P4 兜底。
- 完成判据：所有 P0/P1 用户动作都有 required-data 键；当前缺口全部有归属和阻断批次。
- 回滚：删除新增 manifest/审计脚本与测试，撤销文档改动。

### F2：身份、组织和项目范围

- 目标：用户登录后看到的人、公司、项目和职责是正确的。
- 范围：demo 数据载体中的公司访问、部门、岗位、员工、用户、角色、项目成员和项目范围。
- 必须验证：业务全功能账号、项目经理、财务、合同、采购/物资、成本、管理层、配置管理员；
  至少一个无权限/跨公司负例。
- 完成判据：每角色登录返回正确 `role_surface`、默认路由、非空首屏任务/项目；
  项目成员和作用域与页面可见记录一致。
- 回滚：回退 demo 用户/成员数据与对应回读断言；不修改产品或全库重建。

### F3：业务主数据与表单可用性

- 目标：用户在真实表单中能选到完整、有效、当前的数据。
- 范围：业主/客户/供应商/分包商、联系人、银行账户、税种税率、付款条件、计量单位、
  材料目录/价格、项目字典、成本科目、合同/资料类型。
- 验收：通过公开契约读取表单候选集；关键字段非空；不能只证明表中有记录。
- 阻断：任何选项依赖前端推导、字段缺失不能保存、或必须由管理员猜值，登记产品/数据缺口。
- 回滚：回退具体 XML/seed 文件与回读断言；不删除用户历史。

### F4：审批、编号和权限基础配置

- 目标：第一笔业务提交后真的有人能审批，且不同角色边界正确。
- 范围：审批策略、步骤、评审人/范围、编号规则、菜单/动作/能力、数据规则。
- 所有配置必须通过既有 P3 变更集/发布入口；禁止直接写 `ir.config_parameter`。
- 验收：提交生成审批实例；每个 pending review 至少有真实内部用户；授权人可办理，
  未授权人拒绝；编号符合当前规则。
- 回滚：回退变更集/配置版本；保留审计。

### F5：项目基线及提交前就绪

- 目标：项目从“可创建”变成“可办理”，用户不在提交后才遇到隐藏前置。
- 范围：项目主档、负责人、成员、资金基线、预算、BOQ/WBS、合同/采购依据、收付款账户。
- 若产品没有 `baseline.readiness` 类后端投影，只登记 P1/P3 缺口并以 P4 manifest 作诊断，
  不在前端或 demo 用静态提示冒充产品就绪契约。
- 验收：ready/partial/blocked/no-data 四态；每个 blocked 原因有服务端来源和下一步。
- 回滚：回退 demo 项目基线数据与断言；不改变产品守卫。

### F6：API 驱动的真实用户业务链

- 目标：用 API 验证系统能力确实能按用户操作推进，而不只是校验 ORM 数据存在。
- 链路：login → system.init → ui.contract → 读取/创建草稿 → submit → 逐级审批 →
  结算/付款/付款登记 → 台账/工作台回读。
- 角色：业务全功能账号发起，配置的审批人办理；负例使用无权角色。
- 必须证明：`trace_id`/`request_id`、幂等、负例拒绝、状态回读、审批历史真实、金额日期一致。
- 完成判据：同一冻结场景可重复执行；重复请求不产生重复业务记录或审批实例。
- 回滚：停用场景驱动入口，保留原始日志；不改产品状态来迎合脚本。

### F7：每日运行与体验重置

- 目标：用户每天看到的是系统按业务日历真实推进后的结果。
- 系统事实必须绑定公开业务方法或 intent；无法绑定的步骤不得记成“已推进”。
- 场景至少完成 10 个业务日；未处理的决策保持待办并升级提醒，不自动审批。
- demo tick 推进 demo 自身；experience reset 只清理体验用户产生的记录/编辑/附件/审批/消息，
  不得重置或重建 demo 基线。
- 验收：连续多日 tick、幂等、心跳、角色待办、派生结果更新、基线指纹不变、体验增量清零。
- 回滚：停用新 timer/入口，恢复旧计划；保留 tick 和 reset 原始日志。

### F8：业务全功能账号浏览器验收

- 目标：真实用户从登录到完成一项业务，全程无需技术解释。
- 覆盖：业务全功能账号 + 项目经理、财务、合同、物资、成本、管理层、配置管理员。
- 检查：首页数据非空、下一步动作明确、表单候选可用、审批待办可达、无越权菜单、
  无技术词/错误码/空壳卡；失败截图与 trace 同步归档。
- 完成判据：关键业务链跨角色闭环，页面证据与 API/ORM 回读一致。
- 回滚：验收失败只修 owning layer，不降低数据真实性或绕过审批。

## 6. 立即登记的缺口

| # | 缺口 | 分类 | 归属 | 阻断批次 |
|---|---|---|---|---|
| DUF-01 | `system_fact` 在 tick 中标记为 `unbound`，每日任务不会真实推进业务事实 | demo mechanism defect | P4 | F7 |

| DUF-03 | 角色启动 smoke 只覆盖 3 个角色，未覆盖业务全功能账号，也未断言首屏任务非空 | validation tool defect | P4 | F2/F8 |
| DUF-04 | 多处场景数据仍锚定 2025 年，展示金额存在 `50/100` 样例值 | demo data quality defect | P4 | F3/F8 |

产品层既有缺口继续按 `docs/demo/product_gap_registry_v1.md` 回收，不在本线修复：

## 7. 统一验证

- L1：manifest schema、文档、Agent ledger、场景/reset 离线单测。
- L2：基础数据回读、公开表单候选集、审批/编号/权限定向测试。
- L3：受管 `local.dev` 升级/种子回读，不手工拼 Compose/DB/凭据。
- L4：API 业务链和受影响浏览器路径；仅验受影响用户旅程。
- 任一前层失败阻断后层；零测试不算通过；运行证据必须绑定 environment readback。

## 8. 失败停机

- 基础数据缺项但产品无法给出 repair hint：登记缺口，停止继续补交易数据。
- 审批步骤找不到真实审批人：停止该业务链，不在 demo 自动审批或写终态。
- 页面需要前端按角色名/公司名/模型前缀推导产品语义：停止并转 P0/P1/P3。
- system fact 没有正式 handler：该日保持未推进，不允许 tick 伪报成功。
- 体验重置会触碰 demo XMLID 基线：立即停止，不执行删除。
- 定时任务、数据库、租户或入口身份不一致：environment_defect，停止长超时。
