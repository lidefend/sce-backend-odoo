## 3. 首版展示结构

采用一个主项目串联“合同 → 结算 → 付款 → 经营结果”，选择既有数据中关联真实、金额自洽的案例。
其他状态切片可用于展示，但须标明其历史/待办语境，不能冒充同一用户刚完成的业务结果。

每一步声明：案例/记录引用、业务阶段、说明、角色职责、可执行动作、前置、阻断原因、结果、下一处理者、证据来源。
展示说明可以描述案例背景；动作、可见性、权限、状态、就绪原因必须消费产品契约。

| 面向用户的问题 | 展示内容 | 权威来源 |
|---|---|---|
| 系统能做什么 | 能力、标准/预览标识、适用边界 | 已发布产品能力及成熟度契约 |
| 我能做什么 | 当前职责、可见业务、可执行操作 | 统一角色面、动作授权和数据范围 |
| 现在做什么 | 当前案例任务、下一步、所需资料 | 真实业务记录、待办和就绪契约 |
| 做完有什么变化 | 状态、审批历史、下一角色任务、经营结果 | 动作回读与事实派生投影 |

首版优先演示付款申请办理链，沿用已验证的实际审批配置；不为演示硬编码审批级数或指定岗位。
业务全功能账号用于总览，不能代替普通角色的办理及拒绝验证。

## 5. 首版最小验收包

1. 展示走读：经营概览 → 案例 → 明细，可解释并追溯展示指标。
2. 用户办理：经办提交 → 实际审批人办理 → 经办回看结果；至少一条真实浏览器闭环。
3. 边界：无权账号拒绝、缺前置明确提示；预览标识不授予或剥夺业务权限。
4. 体验保护：区分展示基线与体验增量；验证操作归属、恢复/清理及基线指纹，覆盖审批/附件/消息等实际受影响对象。

每条记录版本、角色、案例、操作、预期、实际结果、环境 readback、原始日志/截图与请求关联。
以真实初次使用者无口头指路完成指定任务作为最终引导验收；自动化通过不替代该观察。

按依赖指纹复用未变结果；先 L1/L2，后受影响运行时和页面。只新增或重跑受影响集合，
不重新遍历全部菜单/角色。最终冻结按仓库规定执行必要交付门禁；零测试、旧环境结果不算新验收。
