# 产品菜单治理专题计划

> 状态：专题规划草案，允许启动“只读盘点与方案设计”，不授权直接修改正式菜单。  
> 总控约束：受根目录 [`README.md`](../../README.md) 的单一真相源、环境矩阵、分支治理和发布门禁约束。  
> 目标：把已有产品能力组织成稳定、易理解、按权限准确呈现的三级菜单体系，而不是简单改名或增加前端静态菜单。

## 1. 现状结论

产品已经具有菜单，并且菜单资产规模较大。基于主仓库当前源码的静态初查：

- `smart_construction_core/views` 中发现 320 个 `<menuitem>` 声明、304 个唯一菜单 ID；约 250 个菜单绑定 action，54 个为分组容器。
- 菜单主要来源至少包括 `menu_root.xml`、`menu_centers.xml`、`menu_business_taxonomy.xml`、`menu_business_taxonomy_groups.xml`、`menu.xml`、`menu_finance_center.xml` 及兼容/历史文件。
- 前端已有导航壳、图标、展开/活动/折叠状态和菜单解析能力，因此本专题不是重写侧边栏组件。
- 已观察到重复中心、同义项、技术性后缀、临时状态词、动作型入口与业务对象混排等风险，例如“预算/成本”“项目管理（后台）”“库存统计表（新）”“快速创建项目”“待我审批（项目合同）”。
- 静态数量不等于用户实际可见数量。最终结论必须以运行时角色、公司、数据库、菜单 contract 和 action 可达性审计为准。

因此，当前问题定义为：**菜单能力存在，但缺少可证明的能力覆盖账、统一命名词典、稳定三级分类和角色化认知负载门禁。**

## 2. 专题边界

### 2.1 包含

- 全量菜单、action、权限组、路由、图标和产品能力的只读资产盘点。
- 正式产品中文命名、一级/二级/三级信息架构设计。
- 重复、孤儿、无 action 容器、不可达、隐藏、历史兼容和管理员菜单识别。
- 角色化可见菜单矩阵，以及桌面、平板、移动端导航呈现验收。
- 菜单迁移映射、兼容、feature flag、回退与结构化证据。

### 2.2 不包含

- 不改变模型 ACL、记录规则、业务权限或 action 业务行为。
- 不通过前端中文、模型名或 URL 猜测菜单归属。
- 不复制 BOSS/PUMA、Oracle、Procore 或 Autodesk 的菜单文字和层级。
- 不把“我的待办”“待我审批”按业务域重复铺设；任务聚合优先进入工作台。
- 不在未完成运行时审计前删除 XML ID、合并 action 或迁移数据库记录。

## 3. 行业标杆对标框架

对标关注信息架构原则，不照搬厂商界面：

| 标杆 | 官方能力分组启示 | 本产品需要验证的映射 |
| --- | --- | --- |
| [Oracle Primavera Unifier](https://www.oracle.com/construction-engineering/primavera-unifier-project-controls-asset-management/) | 以项目全生命周期连接计划、执行、成本、合同、资金和运营 | 项目、合同、成本、资金不应形成彼此割裂的重复入口 |
| [Autodesk Construction Cloud](https://construction.autodesk.com/) | 围绕文档、投标、模型、施工、质量安全、成本等工作流组织 | 生产现场能力应按用户任务归集，而不是按后端模型罗列 |
| [Autodesk Cost Management](https://construction.autodesk.com/workflows/construction-cost-management/) | 预算、承诺、变更、预测等成本活动形成连续流程 | 预算、合同、变更、结算、付款的入口关系需可解释 |
| [Procore](https://www.procore.com/) | 强调项目执行、财务和协作的一体化角色体验 | 公司级与项目级上下文要明确，避免同名入口含义不同 |
| BOSS/PUMA 参考系统 | 轻层级、业务化短命名、稳定图标与状态表达 | 只对齐可用性和视觉语法，不复制其业务事实或权限模型 |

对标输出必须记录采样日期、版本/页面、用户角色、截图或公开来源、观察结论和“不适用原因”。营销页只能证明能力分类，不能证明实际菜单层级；真实导航结论需来自可合法访问的产品会话或官方帮助文档。

## 4. 菜单与能力资产账

建立机器可读 `menu_capability_inventory.json`，每个菜单至少记录：

```json
{
  "menu_xmlid": "smart_construction_core.menu_sc_customer_partner",
  "source_file": ".../menu_business_taxonomy.xml",
  "current_name": "客户",
  "parent_xmlid": "...menu_sc_master_data_center",
  "level": 3,
  "sequence": 1,
  "action_xmlid": "...action_sc_customer_partner",
  "capability_key": "master_data.customer.read",
  "product_layer": "P1",
  "context": "company",
  "audience_roles": ["contact_manager"],
  "runtime_visible": true,
  "route_reachable": true,
  "proposed_path": ["基础资料", "往来单位", "客户"],
  "decision": "keep|rename|move|merge|hide|retire|investigate",
  "evidence_refs": []
}
```

菜单不得仅凭 action 存在就认定为产品能力。完整映射链为：

```text
产品能力 → 权限/角色 → menu XML ID → action XML ID
→ 统一页面契约/路由 → 运行时可见与可达 → 三层正式名称
```

必须分别报告：

- 有能力、有 action、有菜单且可达；
- 有能力、有 action、无菜单（可能为嵌入动作或真实缺口）；
- 有菜单、action 无效或页面不可达；
- 多个菜单指向同一 action；
- 同一能力存在多个名称或多个父级；
- 仅管理员、历史兼容、验收或隐藏组可见的非正式入口。

## 5. 正式命名规范

### 5.1 总体规则

- 面向业务人员使用稳定业务名词，不暴露模型、技术架构、后台、legacy、runtime、fact、projection 等实现词。
- 一级菜单使用业务域名词；二级菜单使用业务子域或连续流程；三级叶子使用用户可识别的业务对象/台账/单据/报表。
- 同一层级采用一致语法，原则上不混用“中心、管理、办理、台账、列表”等不同抽象层级。
- 名称优先 2–6 个汉字；确需限定范围时不超过 10 个汉字。括号只用于法律或业务上不可省略的类型，不用于临时说明。
- 禁止 `/`、`（新）`、`（后台）`、版本号、角色名、重复上级词和技术缩写；WBS 等行业缩写必须有统一中文名称及帮助文本。
- “新建、快速创建、导入、审批”通常是页面动作，不单独占据全局菜单；高频个人任务进入“工作台”。
- “台账”仅用于持续累积、可检索追溯的正式业务记录；普通对象列表不滥用“台账”。
- 报表统一使用业务指标或对象名称；“报表、统计表、分析”按展示目的区分，不以页面组件命名。

### 5.2 三级语义

| 层级 | 回答的问题 | 示例 | 禁止 |
| --- | --- | --- | --- |
| 一级 | 我在哪个业务域工作？ | 项目管理、经营管理、生产管理 | 具体单据、动作、角色名称 |
| 二级 | 该业务域中的哪段流程？ | 合同管理、物资管理、费用报销 | 同时绑定大量无关 action |
| 三级 | 我要处理哪类对象或结果？ | 收入合同、采购订单、报销申请 | 第四级目录、技术模型名 |

最大正式深度为三级。若现有结构超过三级，优先使用页面内 tabs、筛选、场景入口或项目上下文导航消化，不继续增加菜单层级。

## 6. 候选一级/二级归集框架

下表是审计起点，不是最终菜单配置；须由能力资产账、角色任务和产品负责人共同确认。

| 一级候选 | 二级候选 | 典型三级叶子 |
| --- | --- | --- |
| 工作台 | 我的工作、预警提醒 | 我的待办、我的审批、我的项目 |
| 项目管理 | 项目立项、项目台账、项目策划、项目资料 | 立项申请、项目台账、工程结构、工程资料 |
| 经营管理 | 投标管理、合同管理、成本管理、结算管理 | 投标项目、收入合同、支出合同、项目预算、成本台账 |
| 生产管理 | 施工管理、物资管理、分包管理、设备管理、质量安全 | 施工日志、进度计量、物资计划、采购订单、分包合同 |
| 资金财务 | 收付款管理、发票税务、费用报销、资金账户、保证金 | 收款登记、付款申请、发票登记、报销申请、资金调拨 |
| 数据分析 | 经营分析、项目分析、成本报表、财务报表 | 项目经营分析、成本统计、资金驾驶舱 |
| 基础资料 | 组织人员、往来单位、业务字典 | 组织架构、客户、供应商、成本科目 |
| 系统管理 | 权限与账号、流程配置、业务配置、运行审计 | 用户角色、流程定义、配置工作台、操作日志 |

需要专题评审的交叉能力：合同究竟归“经营管理”还是独立一级；成本管理是否独立一级；工程资料归项目还是生产；人事行政是否形成独立一级。这些必须依据真实角色使用频率和产品边界决定，不能由前端单独拍板。

## 7. 信息架构量化约束

- 单一角色桌面一级菜单目标为 7±2 个；超过 9 个必须提供角色任务证据。
- 单个二级分组建议不超过 9 个可见项；三级叶子超过 12 个时必须拆分流程或转为页面内组织。
- 业务用户可见深度 ≤3；管理员也不得用第四层堆放配置。
- 同一角色同义菜单为 0；临时/技术命名为 0；不可达菜单为 0；无权限 action 暴露为 0。
- 高频任务（依据日志前 20%）从工作台或一级入口到达不超过 2 次点击。
- 菜单展开后的横向溢出为 0；长名称必须先治理文案，再使用截断和 tooltip。
- 菜单稳定性优先于“看起来更整齐”：XML ID 和 action 默认保持稳定，改名/迁移不等于重建记录。

## 8. 实施阶段

| 阶段 | 工作 | 退出条件 |
| --- | --- | --- |
| M0 基线冻结 | 记录产品 SHA、数据库、角色、运行菜单 contract 和截图 | 静态与运行时证据绑定同一 SHA |
| M1 全量盘点 | 生成菜单/action/权限/路由/能力资产账 | 304 个初查 ID 全部有处置状态或差异解释 |
| M2 标杆与用户任务 | 采样行业标杆、角色访谈/日志、高频任务 | 每个一级域有事实依据和不适用说明 |
| M3 命名与归集 | 形成现状树、候选树、逐项迁移映射和术语表 | 无未决重复名；每项移动可追溯 |
| M4 原型验收 | 用真实权限数据生成只读导航原型 | 目标角色、五视口、键盘和图标验收通过 |
| M5 受控迁移 | feature flag 下改名/移动，保持 XML ID/action/权限 | 新旧 contract 兼容，历史配置预检通过 |
| M6 日常环境验收 | 部署候选，核对菜单数、路由、字段和权限 | 0 漂移、0 不可达、0 越权、0 控制台错误 |
| M7 分批发布 | 角色批次放量并观察 | 可一键关闭 flag 回到旧树，审计证据完整 |

## 9. 分支与工作包建议

专题分支建议：`feature/product-menu-governance`，使用独立 worktree。

首轮只启动以下工作包：

1. `menu-inventory`：只读静态/运行时资产盘点脚本与 JSON 报告。
2. `capability-mapping`：能力—权限—菜单—action—路由映射。
3. `benchmark-taxonomy`：行业标杆证据与适用性矩阵。
4. `naming-taxonomy`：正式术语表、候选三级树、逐项迁移表。
5. `acceptance-fixtures`：角色、公司、数据库、五视口和历史配置夹具。

M0–M3 通过评审前不得修改菜单 XML、数据库、权限或前端解析逻辑。

## 10. 验收门禁

- 静态 XML ID 集合、运行时菜单集合和前端菜单 contract 三方差异有明确解释。
- 所有可见叶子 action 可达，页面标题、面包屑、活动菜单和浏览器 URL 一致。
- 每个菜单的角色可见性与 action 权限一致；隐藏菜单不能通过直接 URL 越权。
- 桌面 1440/1280/1024、平板 768、移动 390 五视口无溢出，键盘焦点、展开、折叠、搜索和图标完整。
- 旧收藏、旧 URL、历史菜单 XML ID、客户 P2/P3 配置完成兼容预检。
- 中英文或其他语言名称使用翻译资源，不在共享前端硬编码中文判断。
- 结构化验收证据包含产品 SHA、环境、数据库/数据集、角色、菜单路径、action、路由、视口、截图摘要和时间。
- 发布前必须提供旧树恢复开关以及数据库零破坏证明。

## 11. 完成定义

专题完成不是“菜单看起来更整齐”，而是同时满足：

- 产品能力有菜单覆盖结论，真实缺口、嵌入动作和不应暴露项被区分；
- 正式菜单最大三级，命名词典与逐项归集获得产品评审；
- 角色看到的菜单数量、路径和顺序符合其工作任务；
- 权限、action、路由、标题、面包屑、活动态和图标保持一致；
- 日常数据库历史配置兼容，变更可灰度、可观测、可回退；
- 五视口与真实角色验收证据绑定同一候选 SHA。
