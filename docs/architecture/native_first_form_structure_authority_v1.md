# 原生优先表单结构权威决策 v1

## 决策

适用于已有正式 Odoo 表单视图的契约页面：

`入口选定的最终合成原生视图 → 后端保真解析与受约束语义增强 → 唯一有效结构 → 前端正文和导航共同消费`

- 原生合成视图唯一决定基础字段归属、章节名称与顺序、字段 occurrence、按钮、widget、modifiers、关系子视图和协作容器。
- `ui.business.config.contract` 可在 `native_semantic_surface` 模式提供标题、摘要、帮助、风险、动作说明等增强语义；可引用原生视图中的有效字段，但不得声明 `layout`、`sections`、`fields/field_slots`、`columns` 或 `actions/header_buttons` 来重写基础结构。
- 后端输出可同时保留 `layoutContract` 与 `formStructureContract`：前者承载唯一有效原生结构；后者仅承载展示模式和语义投影，不得成为第二棵正文结构。`form_structure_authority=native_authority` 与 `form_presentation_mode=task` 分别表达结构权威和办理呈现，二者不再混为一个开关。
- `native_semantic_surface` 若携带结构键或引用未知模型字段，合成必须显式失败并报告冲突；不得静默选一棵结构，也不得由 P0 按字段名、标题或模型猜测归属。
- 没有显式原生业务锚点的页面继续走既有兼容路径。完整低代码替换布局需要另行定义显式替换模式、权限和冲突校验，不属于本决策。

## 付款入口处置

| 原重复来源 | 处置 | 保留内容 |
| --- | --- | --- |
| 共用 `view_payment_request_form` | 保留为付款/收款基础视图 | 原生字段、按钮、modifiers、关系和协作能力 |
| 付款配置中的 `sections`、完整 `fields`、重复 action 条件 | 从付款配置移除 | 配置仅保留标题和 semantic anchors |
| 正式付款 action | 改绑 `view_payment_request_pay_form`（继承基础视图的 primary view） | 入口 domain、context、模型、权限不变 |
| 前端按 `formStructureContract` 再造业务正文的试验 | 废止 | 使用带 `data-sc-anchor` 的同一原生树生成正文与导航 |
| 付款登记、收款申请配置 | 本轮不改 | 作为共享回归消费者，后续按各自专题判断 |

## 付款有效章节树

| 顺序 | 原生章节 | 字段/能力归属 | 主导航 |
| --- | --- | --- | --- |
| 1 | 基本信息 | 申请分类、项目、收款对象、状态辅助事实 | 是 |
| 2 | 付款依据 | 合同、结算、材料结算及既有口径 | 是 |
| 3 | 收付款信息 | 收付款单位与账户快照 | 是 |
| 4 | 付款明细 | 日期、申请金额及付款明细表 | 是 |
| 5 | 说明与附件 | 备注与既有授权附件 | 是 |
| 6 | 履约与追溯 | 责任余额、来源匹配、付款记录等原生页签 | 否（从属区） |

页面级 alerts、摘要和动作反馈不进入章节树；内部 `group` 只承担布局，除非原生视图显式声明稳定 `data-sc-anchor`，不得升级为一级导航。
