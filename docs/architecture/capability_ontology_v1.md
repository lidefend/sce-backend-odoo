## 1. 正式定义

> 能力（Capability）是一个具有明确业务或技术目的、稳定身份、确定输入输出、可验证执行结果，
> 并且能够独立管理生命周期的可管理、可交付功能单元。

五个必要条件（任一不满足，不构成能力）：

1. 目的明确：解决一个确定的问题，可一句话描述。
2. 身份稳定：不依赖具体菜单、页面、模型名称；换 Provider 不必然改变身份。
3. 契约明确：输入、输出、约束和错误语义可描述。
4. 结果可验证：能证明执行成功或失败，有可复现证据。
5. 生命周期独立：可接入、验证、发布、升级、停用、退役。

## 2. 三层分类

| 层 | 名称 | 定义 | 归属 |
| --- | --- | --- | --- |
| L1 | Atomic Capability | 不可再合理拆分的最小独立功能单元 | 能力发布体系 |
| L2 | Composite Capability | 由一个或多个已发布能力组成，具有独立契约、复用价值和可验证结果的组合功能 | 能力发布体系 |
| L3 | Work Scenario | 面向用户目标的工作过程，组织组合能力、页面和入口 | 产品发布体系（Product Composition） |

边界：L1/L2 属于 Capability，进入能力发布；L3 属于 Product Composition，不属于 Capability。
组合能力不是“最小单元”，因此正式定义不出现“最小”，避免与 L2 矛盾。

## 3. 哪些不是能力

| 对象 | 是否独立构成能力 | 原因 |
| --- | --- | --- |
| Odoo Model | 否 | 数据和业务执行载体 |
| Odoo Action | 否 | 导航或执行载体 |
| Intent | 不一定 | 需有独立功能语义 |
| 字段 | 否 | 能力的数据结构组成 |
| 页面 Scene | 否 | 用户交互呈现 |
| Menu | 否 | 入口 |
| API | 不一定 | 仅当有独立功能契约 |
| AI 模型 | 不一定 | 模型本身不等于可交付功能 |
| 工程计算服务 | 可以 | 满足定义与独立验证条件时 |

`project.project` 是模型；“创建项目”才可能是原子能力。一个原子能力可同时依赖 model、
intent handler、原生 action、多个校验规则，但它们是四个载体，不是四个业务能力。

## 4. 能力身份与 Provider 关系

| 对象 | 含义 |
| --- | --- |
| Capability Identity | 能力是什么，稳定身份（capability_key） |
| Provider Binding | 能力由什么实际执行（model/action/intent/service/api/ai） |
| Capability Qualification | 能力达到什么成熟度（preview/standard） |
| Capability Release | 能力是否正式发布、当前版本 |

身份独立于 Provider：换成微服务或 AI 实现，不必然改变能力身份；但 Provider 变化必须触发
依赖指纹与资格重新验证。

## 5. 组合与依赖规则

1. 组合能力通过依赖引用原子能力，不复制实现。
2. 组合能力契约 = 自身组合契约 + 依赖能力版本 + 兼容性约束 + 组合行为。
3. 组合能力成熟度必须验证依赖版本、兼容性和组合行为，不能把子能力资格简单相加。
4. 原子能力变更（版本/资格/退役）触发所有引用它的组合能力重新验证。

## 6. 四个正交维度

能力状态不是单一维度，必须拆成四个正交维度：

| 维度 | 状态或内容 | 权威 |
| --- | --- | --- |
| 身份 Identity | 已登记 / 未登记 | 能力身份目录 |
| 契约 Contract | 已契约化 / 未完成 | 能力契约 |
| 资格 Qualification | 无资格 / Preview / Standard | `capability_maturity.py` |
| 生命周期 Lifecycle | 候选 / 已发布 / 已停用 / 已退役 | 现有发布治理机制 |

资格维度的 preview / standard 由 `capability_maturity.evaluate_maturity` 返回，不负责退役状态；
生命周期由发布治理机制管理。两个维度独立更新。

证据要求：

- `maturity_fingerprint` = f(capability_key, dependencies, criteria)
- receipt 绑定 capability + 依赖指纹 + artifact 执行用例（pass/fail/error/skip）
- 过期、失败、跳过、重复证据一律拒绝

## 7. 正例、反例与边界

| 类型 | 案例 | 判定 |
| --- | --- | --- |
| 正例 | 创建项目 | Atomic：明确目的、可验证、独立生命周期 |
| 正例 | 项目成本分析 | Composite：组合查询/成本计算等原子能力 |
| 正例 | 完成合同审批 | Work Scenario（L3，产品组合） |
| 反例 | `project.project` 模型 | 载体，非能力 |
| 反例 | `action_project_initiation` | 执行载体，非能力身份 |
| 反例 | `menu_sc_project_project` | 入口，非能力 |
| 边界 | `project.dashboard.enter` | 需有独立功能语义与契约才可作原子能力 |
| 边界 | 工程图纸识别 AI 服务 | 有独立契约与验证时可为原子能力 |
| 反例 | “打开项目列表页” | 若只是导航行为、无独立查询功能与可验证结果，不构成原子能力 |
| 正例 | “查询项目（按条件/分页/权限）” | 有输入、输出、可验证结果，构成能力 |

## 8. 与现有资产收敛的关系

B0 不直接宣布旧目录中的每一条资产都是能力。现有模型、菜单、Action、Intent 和页面必须按
上述五条件与三层分类重新核对。候选目录、迁移计划和 provider binding 由后续 CAP-01B/C
文档与工具维护，不能反向修改本体的定义。

## 9. 关键边界

### 9.1 最小能力边界

“项目创建 / 项目查询 / 项目更新”是否各为独立原子能力，判据是五条件，不是按钮数量或模型数量：

- 三者共享 `project.project` 模型，但目的不同、输入输出不同、验证结果不同，可构成三个原子能力。
- 不能因共享模型合并为一个“项目管理”原子能力。
- 也不能因存在三个入口就机械拆分；只有各自满足“独立契约 + 可验证结果”才成立。

### 9.2 组合能力与工作场景

- 组合能力：自身有稳定身份、可复用、可独立发布与验证。
- 工作场景：面向某个用户目标的一次完整过程编排，依赖入口、页面、角色和步骤，不独立发布为能力。
- 若一组能力只被一个场景按固定步骤使用、无独立复用和验证价值，则保持为场景编排。

### 9.3 身份与资格解耦

- 能力身份存在不等于已发布。
- 能力可被识别不等于可被产品引用。
- 未发布能力可作为候选资产登记，但不得进入正式产品交付引用。
- 身份、契约化、资格和发布是四个独立状态，不互相绑定。

### 9.4 能力与产品生命周期解耦

- 一个原子能力可被多个组合能力使用，一个组合能力可被多个工作场景使用。
- 产品停用或退役不得误退役仍被其他产品引用的能力。
- 能力退役由引用闭合检查驱动，不由任何单一产品发布状态驱动。

### 9.5 Provider 变化与身份变化

- 语义兼容：保持能力身份，升级 Provider 版本并重新验证。
- 语义不兼容：需要新能力版本或新能力身份，不能只改 Provider。

### 9.6 独立生命周期不等于独立部署

独立生命周期指能独立管理资格、版本、引用、停用和退役，不要求物理独立部署。禁止为了满足
能力定义而过度拆分微服务。
