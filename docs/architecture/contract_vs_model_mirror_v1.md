# 契约与模型镜像的关系 v1

## 一句话

「契约」是运行时页面契约的统称；「镜像」是其中一类契约——绑定到**模型平面**、
只承载结构性元数据的稀疏注解契约。

关键边界：**可见性不归模型，也不归镜像**。一个字段是否可见，本来就应该由
「结构视图」+「权限动态计算」决定：结构视图决定字段是否进入渲染树，权限
（`groups` / ACL）在运行时动态决定当前身份能否看到该字段。把可见性写进模型
（或写进镜像的 `fields` 可见/只读/必填）是最容易混淆的做法，属于越界。

一句话口径：**只需要「模型 + 视图 + 权限」**。

- 模型：字段是否存在（`_fields`）。
- 视图：字段是否进入原生渲染树（结构）。
- 权限：`groups` / ACL 在运行时动态决定当前身份是否可见。

除此之外不需要任何模型级可见性声明；解析器只组合 Odoo 原生语义，不改变它。

## 三类契约，三种权威

同一个模型通常同时存在三类 `ui.business.config.contract`：

| 契约 | XMLID 特征 | 绑定平面 | 权威内容 | 退役规则 |
| --- | --- | --- | --- | --- |
| 模型镜像 | `*_form_structure_generated` | 模型（无 action） | 结构性占位；**不得**声明字段级可见/只读/必填 | 结构权威被原生视图接管后退役 |
| 入口契约 | `*_productized_form_v1` / `*_native_v1` | 入口 action | `native_semantic_surface` + 稀疏 `semantic_anchors`（summary/audit 等角色） | 入口仍开放时保留；body 副本退役 |
| 原生视图 | `ir.ui.view`（`view_*_form`） | 模型 | 章节、字段顺序、布局、导航锚点 | 随产品基线演进 |

可见性 / 只读 / 必填的权威：

- 可见性 = 原生视图结构（字段在不在渲染树）+ 运行时权限（`groups`、ACL）动态计算。
- 只读 = 原生视图 `readonly` 表达式 + 状态/权限。
- 必填 = 原生视图 `required` + 模型约束。

镜像与入口契约都**不得**把这些写死成模型级 `fields` 语义；它们最多声明
结构性元数据（哪些字段属于哪个语义锚点），可见性永远由原生能力动态计算。

## 镜像与契约的关系

镜像**是**契约，不是契约之外的另一种东西。它是在「原生视图接管结构」之后，
保留下来的模型平面结构占位：

- 原生视图拥有**结构**（哪个字段在哪个章节、什么顺序）。
- 入口契约拥有**入口语义锚点**（这个入口把哪些字段标为 summary/audit）。
- 模型镜像只做**模型级结构占位**；它不拥有可见/只读/必填——那些由原生视图与权限动态计算。

三者不重叠：镜像不声明 `sections`、不声明 `composition_mode`、不绑定 `action_id`；
入口契约不声明 `sections`/`layout`，只留 `semantic_anchors`；原生视图不把可见性写成模型语义。

## 判定口径

一个 `*_form_structure_generated` 记录是否应保留 active，取决于它是否仍承载
「模型级结构占位」：

- 保留：模型仍需要跨入口统一的结构占位（例如 `sc.labor.usage`、
  `sc.equipment.usage`、`sc.subcontract.register`、`sc.construction.diary`、
  `sc.project.document`、`sc.safety.issue`、`project.progress.entry`）。
- 退役：模型的结构与字段语义都已被原生视图完整接管，历史镜像只剩墓碑
  （active=False，`native_guidance_form_retirement.xml` 显式退役）。

镜像不得拥有 `action_id`，不得声明结构章节，更不得声明字段级可见/只读/必填；
入口契约不得把模型镜像当作自己的第二结构所有者。一处声明只能有一个权威：
结构归原生视图，可见/只读/必填归「原生视图 + 权限动态计算」，入口语义锚点归入口契约。

## 载体分类与 div 的特殊情况

原生视图里元素载体有三种语义，不能混用：

| 载体 | 语义 | 会不会成为章节/导航项 |
| --- | --- | --- |
| `<field>` | 业务事实：可录入、参与校验、作为字段进契约 | 否（字段本身） |
| `<group>` / `<page>` | 业务分区：有标题、进导航、由原生章节渲染器提升为章节 | 是 |
| `<div>` | 纯呈现容器：只做布局/样式，不进章节、不产生导航项 | 否 |

**什么时候必须用 `div`**：当元素既不是业务事实、也不能成为业务分区时——典型是
计算出来的辅助反馈 / 提示态（`processing_advisory`）。它不能写成 `<group>`/`<page>`，
否则原生章节渲染器会把它提升成一个带导航项的章节，空提示还会占位显示「—」；
它也不只是裸 `<field>`，因为需要一块带样式、能整体显隐的呈现区。

反馈宿主的固定形态（也是解析器认得的反馈面）：

```xml
<div class="alert alert-info" role="status" invisible="not processing_advisory">
    <field name="processing_advisory" readonly="1" nolabel="1"/>
</div>
```

- `class="alert alert-info"`：纯呈现样式。
- `role="status"`：这是状态反馈，不是表单事实。
- `invisible="not processing_advisory"`：空提示时整块不显示，不显示占位符。
- 字段 `readonly="1" nolabel="1"`：只读、不带标签。

`div` 是「不是章节、不是事实」时的唯一载体；它不改变 Odoo 语义，解析器把它当作
布局节点组合进契约，而不会误造一个业务章节。
