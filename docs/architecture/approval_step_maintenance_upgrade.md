# 审批步骤维护与升级边界

基线 main `f79d29f55a22d6dbaec778237fbf710a12b6f4b3`。P1 修复默认模板的写入权限，P4 只扩展现有 local.test 的一次性升级演练。不改前端排序、运行时回排、审批引擎、付款执行或撤销。

## 初始化与维护权威

`approval_policy_tier_sync.xml` 仅在首次安装调用模板初始化；`apply_user_visible_approval_templates()` 同时要求 smart_construction_core 处于 `to install`，并跳过已有初始化标记的政策。这样直接重复调用也不能将已安装库的管理员配置重置。

- 干净安装：现有种子政策按当前完整模板建立初始步骤。
- 已有库升级：保留已有步骤 ID、顺序、岗位、金额条件、启停和已删除步骤；不以“缺少步骤”推定需要恢复。
- 新模板或模板新增步骤：干净安装采用最新模板；既有库不自动补入或替换。管理员经已有“审批规则 → 步骤”明确采用，政策模式仍通过对应的正式入口维护。不得增加隐式升级补丁重置既有配置。
- 审批步骤 XML 种子显式设置 `forcecreate="0"`：首次安装仍创建，升级不重建被初始化替换或被管理员删除的步骤。新增步骤也须经正式维护明确补入，不能靠 XML 缺失记录重建绕过初始化边界。
- 升级继续调用 `sync_all_tier_definitions`，读取维护结果生成审批定义；这不是第二份维护来源。

## 申请何时绑定顺序

提交经过 `payment.request.action_submit → _route_submitted_approval → sc.approval.policy._start_submission_review → request_validation`。OCA 按 tier.definition 的优先级读取定义，将当时顺序写入 tier.review.sequence；在途申请优先使用已有实例，不能重新初始化。

本轮只调整初始化写入。tier.review 的岗位、名称、approve_sequence 等仍存在关联定义字段，不能宣称既有机制对所有政策字段都做了完整冻结；本轮只验步骤顺序调整和升级，不改变既有在途处理机制。

## 真实 ORM 和升级验收

沿用现有受管入口：

```sh
make local.test.test MODULE=smart_construction_core TEST_TAGS=approval_step_upgrade LOCAL_TEST_UPGRADE_SCENARIO=payment_approval_order
```

仍由 local_test_runner 独占既有 sc_test、校验私有配置/卷/镜像/源码身份，并在每个完整尝试开始时重建一次测试库。新增有界场景在同一个锁及临时 carrier 内：安装并跑非零 ORM 测试 → 正式表单维护/新申请审批 → 实际 `-u smart_construction_core` → 新申请审批 → 第二次实际升级 → 再次新申请审批。各阶段失败即退出，无自动重试，无阶段间重建库。

测试数据使用现有 BusinessTransactionCase 的显式合成公司登记机制。配置由非 sudo 业务配置用户通过原生 Form 的步骤编辑完成；提交和审批使用合成非 sudo 用户。仅创建测试申请并审批，不执行支付或撤销。旧顺序的在途申请贯穿升级，核对实例 ID、sequence、status 不变，最后按原顺序完成审批。

原始日志、三个阶段的配置前后值、申请/审批实例 ID、逐步流转及源码指纹由当前 run 统一索引。函数隔离回归和真实升级结果分开登记；未实际通过前不声称验收完成。
