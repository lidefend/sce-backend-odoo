# 角色、能力与审批权限边界 v1

## 1. 目的

本文统一 Odoo 原生权限体系与 SCE 行业权限模型，解决四类事实混用：

- 角色身份；
- 能力授权；
- Odoo 技术权限；
- 用户配置的审批链。

本文是权限设计判断入口，不替代原生 ACL、记录规则、字段权限或 Tier Validation。

## 2. Odoo 原生权限链

| 层 | Odoo 机制 | 事实与边界 |
| --- | --- | --- |
| 组继承 | `res.groups.implied_ids` / `trans_implied_ids` | 组可以传递继承；Odoo 会把用户所属组及传递 implied 组物化到 `res.users.groups_id` |
| 用户判断 | `res.users.has_group()` | 检查用户在完整组闭包中是否持有目标组；它本身不执行模型 ACL 或记录规则 |
| 模型 ACL | `ir.model.access` | 按模型和“读/写/建/删”授权；用户任一匹配 ACL 组或全局 ACL 可授权该操作 |
| 记录规则 | `ir.rule` | 全局规则 AND；同一操作下命中的非全局规则 OR；最终结果再与全局规则 AND |
| 字段权限 | 字段 `groups` | 控制字段可见、可读写或可编辑 |
| 菜单/动作/视图 | `groups` / `groups_id` | 控制 UI 入口与动作可见性，不替代模型 ACL 和记录规则 |
| 多公司 | `allowed_company_ids` / `company_ids` / 公司记录规则 | 公司范围与功能授权是两个维度，不能互相替代 |
| ORM 校验 | `check_access_rights()` / `check_access_rule()` | 分别校验 ACL 与记录规则；`sudo()` 会绕过这些访问层，不等于绕过业务规则 |

关键约束：

- 原生 Odoo 不区分“角色组”和“能力组”，这种分类必须由产品契约和静态守卫明确声明。
- 角色组和能力组最终都以 `res.groups` 实现，因此不能依赖名称猜测语义。
- 名称不是授权证明；真正的授权结果仍由 ACL、记录规则、字段/菜单/动作组和业务代码共同决定。

## 3. SCE 权限模型

| 对象 | 职责 | 禁止事项 |
| --- | --- | --- |
| 角色组 | 表达用户身份、岗位组合和多个角色并存 | 不直接出现在 ACL、记录规则、字段、菜单或动作授权中 |
| 能力组 | 表达可执行的能力，并作为 ACL、记录规则、字段、菜单和动作的授权载体 | 不反向 implied 角色组，不冒充用户身份 |
| Odoo 原生技术组 | 承载 Odoo 字段、ACL、记录规则等实现依赖 | 不直接暴露给业务用户配置 |
| 审批岗位 | 产品提供的审批范围词汇，映射到能力组 | 不映射到角色组；不写死具体审批人 |
| Tier 审批实例 | 保存用户实际配置产生的审批步骤和当前审批人 | 不被产品模板或角色静态判断覆盖 |

标准继承方向：

```text
用户
  → 一个或多个角色组
  → 一个或多个能力组
  → Odoo 原生技术组
  → ACL / 记录规则 / 字段 / 菜单 / 动作
```

禁止方向：

```text
能力组 → 角色组
ACL / 记录规则 / 字段 / 菜单 / 动作 → 角色组
产品代码 → 固定角色即具体审批人
```

## 4. 多角色语义

- `role_codes`：用户实际持有的全部角色组，可以包含多个角色。
- `primary_role_code`：按产品优先级选出的主角色，只用于默认展示和入口选择。
- `surface_role_codes`：受 `exclusive_surface` 约束的页面表面角色，不改变真实权限并集。
- 角色的 UI 顺序不得改变能力并集；能力授权始终来自全部实际角色产生的能力组闭包。

因此，业务配置管理员角色可以同时持有所需的超集角色和工作角色；重复职责必须通过组关系和能力组收敛，而不是通过删除角色的真实身份事实来隐藏。

## 5. 审批链语义

审批是企业配置的业务流程解释器：

1. 产品定义可审批的业务模型、审批岗位词汇、步骤字段、金额条件、顺序和可配置范围。
2. 用户按企业业务配置具体审批步骤与审批能力组。
3. 配置存在时，提交只产生审批实例，由当前 Tier 审批人推进。
4. 配置为“无需审批”时，提交在同一业务事务中自动通过首段审批并推进到业务允许状态。
5. 后续办理只消费已经批准的提交事实，不重新解释后来变化的审批配置。
6. 审批权限以当前 `tier.review` 的审批组和 `can_review` 为准，不以固定角色或固定“管理层”组为准。

审批不是 Odoo ACL 的替代品：

- ACL/记录规则决定用户能否读取、写入该业务记录；
- Tier 决定该记录当前能否审批、由谁审批；
- 业务规则决定审批通过后能否进入下一业务状态；
- `sudo()` 不得用于绕过用户审批身份。

## 6. 当前实现事实与缺口

已完成的本轮收敛：

- 角色目录中的显式身份绑定改为角色组；
- 能力组作为 fallback 和授权载体；
- 业务配置管理员、业务全功能、成本、项目成员、项目经理的显式身份与能力 fallback 分离；
- 租户业务管理员和管理层审批的 ACL、记录规则、视图、业务判断改为能力组；
- 审批岗位映射改为能力组；
- 付款审批入口允许当前 Tier 审批人进入，实际动作仍要求 `can_review`；
- demo `wutao` 和验收夹具统一使用角色组表达身份；
- 增加静态守卫，阻止 ACL、记录规则和视图直接引用角色组。
- P0 新增统一 `smart_core.workflow.contract` 服务，负责契约形状、审批阶段、
  动作可用性、状态栏和 fail-closed 一致性校验；
- P0 新增统一 `workflowContract` 注入点，行业模块不再负责通用契约注入；
- P1 `sc.workflow.contract.service` 退化为兼容门面和 Profile/业务证据提供器；
- `smart_construction_core` 通过显式 extension hooks 向 P0 提供行业 Profile、
  业务证据和审批配置是否存在。

下一批必须逐模型确认：

- 哪些动作是业务单据提交，必须进入审批链；
- 哪些动作只是执行/整改/关闭状态，不应被误建模为审批；
- 每个已接入审批的业务模型都必须在“无审批配置”时自动推进，在“有审批配置”时只由当前 Tier 推进；
- 不允许用统一装饰器盲目覆盖全部模型。

## 7. 验收要求

### 角色与能力

- 角色组不直接出现在 ACL、记录规则、字段、菜单或动作授权中；
- 显式身份映射只引用角色组；
- 能力 fallback 只引用能力组；
- 能力组不得 implied 角色组；
- 用户可持有多个角色，权限按能力组闭包并集计算。

### 审批

- 无审批配置：提交后自动通过并推进允许状态；
- 有审批配置：提交后不得直接进入已审批状态；
- 当前 Tier 审批人即使不持有固定的“财务/管理层”能力，也可进入审批动作；
- 非当前 Tier 审批人即使持有高权限角色也不得审批该记录；
- 审批步骤、`reviewer_group_id`、ACL、记录规则和业务判断使用同一能力组；
- 审批配置变化不得改写已生成的审批实例。

### 夹具与 demo

- 身份验收账号使用角色组；
- 能力探针如果只持有能力组，必须明确标记为能力席位，不承诺角色身份；
- 验收夹具不得通过 capability 组伪装成配置管理员角色；
- demo `wutao` 使用业务配置管理员角色组，`demo_full` 使用业务全功能角色组。

## 8. 迁移原则

- 已直接持有配置能力的历史用户，升级时补配置管理员角色组，不删除能力组事实；
- 不根据登录名推断普通用户角色；
- 审批配置中的旧角色组授权必须按精确映射迁移到能力组，并保留原有步骤顺序和能力范围；
- 迁移执行仍须另行提供目标库、精确模块版本、行数预检、备份/恢复和回读断言。
