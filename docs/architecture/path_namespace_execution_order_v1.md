Baseline: `codex/daily-platform-demo-20261018` @ `54a3fa13177c2a9c0aeb0efaf40786cea32089a8`（dirty 时以批次记录为准）

## 通用规则

- 一批一写者；同一工作树不得并行写入。A 批只动服务器与部署事实，不动产品代码；B/C 动代码。
- 每批证据必须绑定精确对象：容器名、镜像 digest、挂载源、源码 HEAD、文件哈希、请求与响应原文。
- 状态使用四层口径分别报告：批次状态｜主线状态｜部署状态｜用户验收状态。
- 不得把“体检通过”当作“机制已建立”；不得把“标签已改”当作“版本已对齐”。
- 证据不足时结论写“未证实”，不写“通过”。

## Batch A：部署事实纠偏

目标：把“有哪些公网入口、每个实例实际跑什么”变成可回读的事实，而不是推断。

写入范围：服务器 `sc-root` 的容器/端口/部署配置；仓库内 `config/ops/` 与部署文档。禁止改产品代码、登录与身份逻辑。

步骤：

1. 全量发布端口盘点：`docker ps` 中所有 `0.0.0.0`/`[::]` 发布，逐一对应 `ss -ltnp`；标记每个端口的用途与批准状态。
2. 公网实测：从外部主机对每个发布端口做 TCP 连通性测试，不只测试 `18081`。记录来源公网 IP、ASN、时间戳，并与同刻 `ss -ltnp` 的 5-tuple 交叉核对；禁止用本机 curl 冒充外部主机。
3. 关闭未批准入口：`18086`（release rehearsal）下线或改绑 `127.0.0.1`；`18089/18090/18091` 同样按批准状态处理。注意 `docker-compose.release-rehearsal.yml` 中 `18086:80` 是全网卡绑定，重建会恢复暴露，处置必须落在 compose 或独立审批的停机动作上。
4. 逐实例身份表：容器 → 镜像 digest → `SC_SOURCE_REVISION` → 挂载源码路径与 HEAD → 容器内全树哈希（排除易变目录，排序后 sha256sum 再取总哈希）→ 进程启动时间 → 前端指纹。抽样哈希不能作为版本证明。
5. 源码/运行身份对齐：以容器内实际加载文件为准修正声明；从 `/proc/<pid>/maps` 或模块 `__file__` 取进程实际加载路径，与挂载树逐一对齐。若挂载在进程生命周期内发生变化，必须重启并重新回读，不能只看当前 checkout。
6. 外部回读：批准入口可用；未批准入口全部不可达。
7. 修正验收口径：把“某端口唯一发布者”改为“全主机发布面清单 + 逐个批准状态”，避免再次以偏概全。

收口证据：

- 全量端口清单与批准状态表；
- 外部连通性原始结果（含时间、来源主机）；
- 每个实例的镜像 digest、挂载源、容器内 HEAD/文件哈希、启动时间；
- 对齐后的 `runtime-version` 与容器内实际文件一致性证明；
- 负向对照：修改 `SC_SOURCE_REVISION` 前后的同一回读断言，证明该字段确实来自声明而非实际代码。

回滚：`18086` 若需恢复，必须独立审批并记录原因；按原 compose 重建会立即恢复公网暴露，不得以“恢复演练”为由长期保留。A 回滚后必须重新执行逐实例身份回读。

明确不做：不改 `login.py`、`auth.py`、`platform_admin.py`；不宣称命名空间已存在。

## Batch B：身份语义纠偏

目标：消除“任何账号都可能被标成平台管理员”的错误语义，同时保持现有登录可用。

写入范围：`addons/smart_core/handlers/login.py`、`addons/smart_core/models/login_routing.py`、`addons/smart_core/security/platform_admin.py` 及对应测试。允许最小前端展示修正，但不得引入命名空间解析。

步骤：

1. 删除无路由兜底返回 `entry_kind=platform_admin` 的行为；兜底必须是显式“未解析”状态，并在契约中可区分。
2. 修正 Demo 库中 `admin -> sc_demo` 的 `entry_kind`：租户库不得声明为平台管理入口。
3. `ensure_platform_default_login_routes()` 只在平台控制实例播种，不在租户库创建平台管理路由。
4. 平台管理员判定加入实例约束：当前数据库必须是被声明的平台控制库；保留组校验，为 C 批的身份域/受众校验留出接口。
5. 保持显式 `db` 通路可用（标注 deprecated），避免 C 批前登录中断。
6. 补测试：无路由兜底、租户路由标记、平台实例判定、租户账号不被误标。

收口证据：

- 平台管理员可在平台入口正常登录；
- 租户账号登录响应不再出现 `entry_kind=platform_admin`；
- 单元测试覆盖上述分支且非零通过：列出精确测试名与计数，并提供负向对照（临时回退修复后同一测试必须失败，附失败输出）；
- 明确声明：本批未实现命名空间隔离。

回滚：单提交回退；不得以“兼容”为由保留错误兜底。

## Batch C：命名空间机制

目标：建立服务端权威解析，路径决定职责，身份绑定命名空间，显式 `db` 冲突被拒绝。

前置：A、B 完成并通过各自收口。C 是唯一允许移除显式 `db` 通路的批次，且必须原子切换。

写入范围：入口 nginx 配置、`smart_core` 命名空间解析与 token 声明、登录处理器、平台 API 命名空间上下文、前端路由与入口契约、测试与验收脚本。

步骤：

1. 命名空间登记：`namespace_id` 不可变；路径/子域为别名；绑定目标库与职责；登记生命周期状态。
2. 服务端解析器：路径 → 命名空间；未知/停用/冲突/歧义返回确定错误；除显式声明的 `/` 重定向外不得有默认租户。
3. 入口路由：`/platform-admin` 与 `/t/<tenant>` 由 nginx 直接分流；不再依赖客户端库头选职责。所有转发 location 必须覆盖客户端自带的 `X-Odoo-DB-Locked`，并增加“客户端 locked 头无效”的回归断言。
3a. 移除 `request.session.db` 回写这一隐藏第二权威（`controllers/intent_dispatcher.py` 附近），否则默认库回落仍有入口。
3b. 路由清单必须是签名清单并带 TTL；过期即拒绝，不得静默沿用旧清单。清单与代码按成对版本登记。
3c. 定稿 `platform_control` 的识别口径：当前 `sc.platform.database.registration.data_purpose` 只有 customer/demo/test，而 duties 声明包含 platform_control；必须在扩展枚举与 duty_key 比对之间明确选择并测试。
4. 身份绑定：目标库原生认证；token 携带 `namespace_id` 与受众；跨命名空间重放拒绝。
5. API 上下文：后续请求保留命名空间；缺失或与 token 不一致即拒绝。
6. 前端：消费入口契约，移除烧录库名作为权威；`X-Odoo-DB` 只能作为候选且不得覆盖解析结果。
7. 原子切换：同一发布窗口内启用解析器，并同时拒绝冲突的显式 `db` 与 `sc.login.default_tenant_db` 默认租户回落；不保留可绕过的过渡通路。入口 nginx 配置哈希与 Odoo 代码 SHA 成对登记，二者不匹配即拒绝切换；切换前签发的 token 按既定策略失效或明确拒绝。
8. 验收：执行 ADR-007 第 8 节全部场景。逐场景保留请求/响应原文与唯一 request-id，并附“pre-C 版本必须失败”的对照证据。
9. 直接发原始 HTTP 携带与解析结果冲突的 `X-Odoo-DB` 与 `?db=`，断言确定 4xx 错误码；只断言“前端未发送”不构成通过。
10. 设置 `sc.login.default_tenant_db` 后请求仍须返回“需要明确入口”，证明默认回落已移除。

收口证据：

- 同名账号、跨域重放、双标签页、退出、公司切换、成员资格撤销的原始请求/响应；组变更后既有会话必须返回 401（区分于“逐请求复核”）；
- 解析器对未知/停用/冲突命名空间的确定错误码；
- 新租户仅发布映射即可访问的证据（无需重建前端）；
- 前端不再依赖构建期库名的代码与运行证据。

回滚：整批回退到 B 收口点；路由映射版本化，回退不修改租户数据。回退必须先处理已签发的 `namespace_id` token（拒绝或失效），不得让旧代码忽略声明而放行。

明确不做：平台首页与能力发布产品闭环；公开注册。

## 排期与依赖

```text
Batch A (环境面, 可与 B 并行)
        \
         > Batch C (需 A+B 收口)
        /
Batch B (代码面)
```

- A 与 B 的写入面不重叠；若共用同一工作树，则仍按“一写者”串行提交，A 以服务器操作与配置证据为主。
- C 不与任何批次并行写入同一工作树。
- 任一批次未收口，不得开始下一批次的验收声明；可以并行准备，但不能并行写入。
- B 回滚需要重启 Odoo，会使 A 的进程启动时间与容器内哈希证据失效；B 回滚后必须重跑 A 的对应回读。
- “一库一客户”目前是 verify-only 不变量：`sc.platform.database.registration.tenant_key` 无唯一约束，`db_name` 才有。若要求运行时强制，须另立批次。

## 禁止的进度表述

- “入口已统一”在 A 收口前不成立（18086 仍可能可达）。
- “平台管理员已隔离”在 B 收口前不成立（兜底误标仍在）。
- “命名空间已建立”在 C 收口前不成立（无服务端解析器）。
- “版本已对齐”在 A 的容器内实际文件核验完成前不成立。
