# 原生视图复用驱动的前端页面设计规范 v1

## 1. 文档目标

本规范用于统一自定义前端页面设计方法：以 Odoo 原生视图作为基础结构来源，后端负责语义解释，前端负责通用渲染，场景层负责产品化增强。

适用范围：
- Odoo 后端视图解析层
- 通用前端渲染层
- 页面场景编排层
- 产品化增强层

## 2. 核心设计思想

页面主路径固定为：

`Odoo 原生视图定义结构 -> 后端解析与语义提升 -> 前端按统一契约渲染 -> 场景层增强编排`

要求：
- 基础页面骨架定义权优先归属原生视图
- 前端禁止“再造一套页面结构”

## 3. 总体原则

### 3.1 原生结构优先
原生已定义结构，前端不得重复定义，包括：字段顺序、group/notebook、header/button box、chatter、modifiers、x2many、tree/form/kanban基础结构。

### 3.2 后端解释优先
前端不解析 XML，不推理业务语义。后端必须输出结构标准化、权限与状态解释、按钮行为、页面推荐布局。

### 3.3 通用渲染优先
优先补通用渲染器能力，不优先写页面特例：List/Form/Kanban/Search/Header/Relation/Block 渲染器。

### 3.4 产品增强外挂
AI 建议、风险预警、下一步动作等必须由原生事实和显式用途、关联对象及触发声明驱动。zone/block 或 task/risk 语义角色不授权常驻主体教程，也不允许前端从只读或非空值推导提示。字段原生 help 通过官方帮助交互展示，动作风险通过声明动作触发；真实字段错误、操作结果和契约缺口状态保留各自来源。

### 3.5 一致性优先
同一业务对象在 Odoo 与自定义前端必须语义一致：字段顺序、按钮语义、状态口径、权限结果不得冲突。

### 3.6 布局与权限分离（2026-10-13）
模型基础视图、动作选定视图和权限裁剪后的运行契约必须分别记录，不得互相代替验收。
动作绑定视图是入口布局基线；相同入口、视图、记录、公司、配置版本和有效模式下，角色权限
不得另选模板、章节、字段顺序或宽度规则。权限负责数据访问、字段／动作可见性、可用性与只读。
隐藏未授权内容不等于授权前端重新编排业务结构，也不得为了保留布局向客户端泄露无权数据。
统一响应式表现由组件体系负责，不以角色为输入；缺失或非法的契约布局参数必须显式停机。
完整职责与验收口径见 `docs/architecture/backend_contract_boundaries.md` 的“视图、布局与权限职责”。

## 4. 页面四层模型

### 4.1 原生定义层（Native View Layer）
来源：Odoo view arch + fields + modifiers + inheritance 合并结果。

### 4.2 结构标准化层（Normalized Structure Layer）
后端统一输出：`view_type/fields/header/button_box/notebook/relations/chatter/search_panel/toolbar_actions`。

### 4.3 页面语义层（Semantic Page Layer）
后端语义提升输出：`zone + block`。

建议 zone：
- `header_zone`
- `summary_zone`
- `detail_zone`
- `relation_zone`
- `action_zone`
- `collaboration_zone`
- `insight_zone`
- `attachment_zone`

建议 block：
- `title_block`
- `status_block`
- `action_bar_block`
- `field_group_block`
- `notebook_block`
- `relation_table_block`
- `stat_button_block`
- `chatter_block`
- `attachment_block`
- `risk_alert_block`（仅显式触发与关联声明，不自动常驻主体）
- `ai_recommendation_block`
- `next_action_block`（仅显式动作交互声明，不凭语义角色生成教程）

### 4.4 产品编排层（Product Orchestration Layer）
场景层消费明确声明的场景增强，不按角色选择或重组页面布局；增强不得改变动作视图的基础结构。

## 5. 页面设计流程

1) 先审原生视图是否可承载基础结构；可承载则禁止重画基础页面。

2) 前端“做不出来”时优先补后端解析输出：语义、modifiers、x2many、按钮行为、分区映射。

3) 前端唯一输入为语义契约：`page/zones/blocks/fields/actions/permissions/ui_hints`。

4) 仅高价值页面做编排增强，普通页面优先通用渲染。

## 6. 后端职责与禁令

### 后端必须输出
- 视图基础定义
- 结构化页面定义
- 字段行为修饰（readonly/required/invisible/domain/context/widget）
- 行为定义（object/action/stat/smart/button）
- 权限与状态解释（可见/可编辑/可执行/不可执行原因）

### 后端禁止
- 将原始 XML 直接下发给前端并要求前端解释业务语义
- 仅返回字段列表并把页面结构责任推给前端
- 同一页面出现多套冲突结构来源

## 7. 前端职责与禁令

### 前端核心职责
- 骨架渲染
- 通用组件映射
- 交互反馈
- 输入管理
- 提交刷新
- 状态展示
- 增强区插槽渲染

### 前端禁止
- 解析 Odoo XML
- 推断权限与按钮可执行性
- 推断业务分区
- 手工改写与原生冲突的字段顺序
- 复刻后端业务规则

## 8. 页面类型规范

### 列表页
复用 tree/search 结构；支持列顺序、过滤、分组、批量操作、分页、状态面板。除产品编排明确要求外，不得手工重排基础列语义。

### 表单页
以 form 为结构源；支持 header/stat/group/notebook/x2many/chatter/modifiers。可美化布局，不得破坏业务结构顺序。

### 看板页
复用 kanban 语义（标题/状态/摘要/动作）。产品增强需基于原始卡片语义，不得重造卡片定义。

### 搜索区
以 search view 为过滤结构来源，前端不得构造与后端不一致的筛选逻辑。

## 9. 产品增强规范

增强能力通过扩展配置注入（scene orchestration / page extension / capability injection），不侵入基础渲染器。

增强层边界：
- 不改写原生字段业务含义
- 不越过后端权限判断
- 只能加语义，不可篡改地基

## 10. 开发治理

### 新页面检查单
1. 原生视图是否可承载基础结构？
2. 后端解析是否输出完整语义？
3. 当前需求属于通用能力还是产品增强？
4. 是否必须做页面特例？
5. 是否破坏通用渲染体系？

### 实施优先级
1. 后端结构解析
2. 前端通用渲染器
3. 语义编排层
4. 产品增强层
5. 页面特例

### 特例准入条件
- 通用渲染不能覆盖核心表达
- 页面高频高价值
- 不破坏通用契约
- 可抽象为可复用模式

## 11. 建议契约输出方向

```json
{
  "meta": {},
  "native_view": {},
  "semantic_page": {
    "layout": "two_column",
    "header": {},
    "zones": [
      {"key": "summary_zone", "blocks": []}
    ]
  },
  "record": {},
  "permissions": {},
  "actions": {}
}
```

必须同时具备：
- 原始来源可追溯
- 语义层可渲染
- 行为层可执行
- 权限层可解释

## 12. 当前阶段执行要求（强制）

从本规范落库起，后续迭代默认遵守以下硬约束：

1. 新页面先做“原生可承载性检查”，再做前端开发。
2. 页面结构问题优先补后端语义输出，不先写前端特判。
3. 前端页面以语义契约为唯一结构输入。
4. 页面特例必须在迭代说明中写明准入理由与退出条件。

## 13. 一句话口径

基础页面由 Odoo 原生视图定义，后端解释为统一语义结构，前端通用渲染，高价值场景再做产品增强。

## 14. 共享前端语义边界（强制）

`AppShell`、`HomeView`、`MyWorkView`、通用列表、共享导航、共享首页/任务/列表组件及其直接 API/composable 属于通用前端运行时，不属于任何行业产品包。该层只能消费正式契约并渲染，不得保存行业或岗位业务字典。

共享层允许拥有的语义仅限：

- 布局、响应式、焦点、加载、空状态、错误和恢复；
- 契约声明的标题、说明、区块、动作、导航节点和上下文；
- 与业务无关的产品通用文案，例如“首页”“返回”“重试”“暂无可用内容”；
- 对后端已裁决结果的排序、折叠和视觉呈现。

共享层禁止：

- 以角色码、登录名、用户组推导首页内容或展示名称；
- 建立 `role -> title/description`、`group_key -> business domain`、`model -> label/layout` 等平行业务字典；
- 通过 scene key、route、model、XML ID、菜单中文关键词推导行业或权限语义；
- 在缺少契约字段时补写项目、合同、结算、付款、经营等行业 fallback；
- 由前端生成待办数量、金额、风险、状态或业务入口；
- 在共享任务卡或列表中直接读取 `project/contract/settlement/payment/partner/amount` 等行业事实字段；业务包必须把可展示事实归一为带 `label/display_role/value` 的 `facts` 契约，搜索和排序同样由契约声明；
- 为满足视觉目标伪造后端未提供的首页区块。

行业产品语义必须由正式 product/page/navigation/work-item contract 提供。契约缺失时，共享层只能显示通用安全空状态并记录契约缺口；不得猜测补齐。

上述规则由 `verify.frontend.shared_surface_semantic_boundary.guard` 强制检查，并进入 `ci.local.quick` 与完整 CI。门禁保护 Shell、Home、My Work、通用列表、任务组件、列表组件及其共享 API/composable；新增共享表面必须同步加入保护清单，不能等发生越界后再补。验收脚本和 fixture 可以引用固定角色或业务对象，但不得被生产运行时代码导入。

### 14.1 三类权威与权责表（强制）

边界不是"都归契约"，而是三类权威彼此分离：

| 类型 | 权威来源 | 前端职责 |
|---|---|---|
| 业务语义与能力 | 有效业务契约，以及其绑定的 Odoo 业务执行能力 | 理解并消费，不重新定义 |
| 受管呈现策略 | 已发布的 Web 呈现配置、产品设计规范、模板适配策略 | 在允许范围内实现，不暗中覆盖 |
| 瞬时交互状态 | 前端当前会话、组件状态与用户操作 | 自主管理，不改变业务含义 |

强制准则：**影响业务含义、合法操作、数据结果和授权范围的决定，必须来自有效业务契约及其绑定的业务运行时；
前端只能决定如何呈现、如何收集输入，以及如何安全地完成交互。缺少必要业务语义时，不得猜测补齐。**

必须来自契约（可显式声明，也可引用契约绑定的权威服务结果）：对象与数据身份、字段值语义（类型/精度/单位/币种/
枚举/空值与"未修改"的区别）、默认与派生值及其口径、校验规则与执行位置、写入能力、业务动作身份与前置条件、
状态与流程转换、关系与明细能力（选择范围/受控引入/唯一性）、查询与统计口径（可查询字段/服务端排序/分页协议）、
授权与产品暴露、错误代码与业务归属、附件与外部动作约束、低代码生效与发布规则。

前端可自主决定（须守住上表约束）：组件与组合选择、栅格/间距/断点、内容承载形式（抽屉/独立页/分步）、
按钮主次与收纳、错误摘要与焦点/滚动/无障碍反馈、列宽与显示偏好、加载与上传进度等瞬时状态、
防抖/防重复提交/异步身份保护、本地草稿与离开保护、本地化与数值排版。

前端可以执行契约声明的规则，但不能成为该规则的唯一保障：端侧校验用于及时反馈，后端仍执行必要约束。

灰区裁决（沿用本规范既有口径，不得由页面自行选择）：

- 业务只读与交互禁用分开：「记录已确认不可修改」来自业务能力，「正在保存不接受二次点击」来自交互条件；
  不得共用一个布尔值再由页面反推权限；字段无效不应一律禁用保存而让用户拿不到纠正反馈。
- 业务隐藏与呈现收纳分开：权限禁止获知的字段不得靠前端折叠"保护"；用户隐藏某列不改变权限、必填或提交语义。
- 业务行身份与端侧位置身份分开：`occurrenceKey`、页签位置是端侧身份；服务端未给精确字段归属时保留表单级错误，不猜字段。
- 业务默认值与界面默认值分开：主题密度可由前端规范决定；默认项目、税率、付款类型、业务日期必须有业务来源；
  没有默认值不等于可以取数组第一项。
- 业务排序与显示排序分开：不得把"只对当前页排序"当作"全部业务数据排序"，不得用已加载记录推断全量统计。
- 页面组装与产品职责分开：可以改承载形式，不得为模板方便删除必要字段、省略业务步骤或把未实现职责写成"不适用"。

### 14.2 缺口必须显现，不得静默补齐（强制）

`undefined`、空数组、`false` 不得同时承载"缺失／显式禁止／合法空集／由后端执行／前端尚不支持"。这几类必须可区分：

| 发现情况 | 定性 | 应改哪里 |
|---|---|---|
| 原生业务事实已有，有效契约没带出来 | 投影缺口 | 契约生产／投影 |
| 业务要求明确，契约无可表达语义 | 表达缺口 | 契约定义及对应执行实现 |
| 契约已表达，前端未使用或用错 | 消费缺陷 | 适配器／运行时 |
| 现有规则、契约与预期互相矛盾 | 规则冲突 | 核清权威依据，不由页面选一方 |
| 当前终端无法正确实现必要能力 | 终端能力缺口 | 明示限制或补端侧实现，不得伪装成功 |

运行时策略：关键语义（权限、写入身份、必要校验、动作绑定）缺失时阻断该操作并保留草稿，不影响已确认安全的读取；
合法声明"无该规则"或"由后端执行"按声明处理；纯呈现配置缺失用统一端侧默认值；精确错误位置缺失但有安全消息时
显示表单级提示；契约版本变化使当前操作失效时保留草稿、结束失效操作并提示，不自动改用新规则继续提交。

**默认拒绝不是遇缺口就停机，而是禁止未知语义被默认为允许。**

最小反例回归（应直接落在既有测试入口，不另建框架）：

1. 删除关键契约语义 → 对应能力明确报缺口或停止，不能继续靠前端兜底办理；
2. 更换标题、标签、列顺序 → 动作身份、规则、授权和业务行身份不变；
3. 只改契约规则、不改页面代码 → 消费行为随规则变化；
4. 只改页面模板／布局、不改契约 → 同一业务意图的输入语义、授权与执行结果不变。

上述四类分别抓：静默补齐、文案猜测、契约不消费、模板越权。

### 14.3 布局契约的职责界限（强制）

Owner 裁决（2026-10-12）：布局契约按职责界限执行；**契约声明的布局能力不回退，也不要求选定组件系统必须完整消费契约能力**。

- 契约侧（P0 `smart_core`）拥有布局**声明**：唯一布局方言（24 单位 `span`）、容器字段网格列数（`columns`）、
  容器分区（`zone`）、区域/表面声明。这些声明构成契约的**能力集合**，允许多于任一消费者当前的使用范围；
  不得为了迁就某个组件系统的内部数据结构而删减，或在契约内引入竞争的第二布局方言。
- 消费侧（采纳方/渲染器）拥有**呈现映射**：组件系统自身的视觉 DTO（如官方 `SceneField.span: full|half`）、
  响应式断点折叠、栅格/间距、落单子行填充等，均属采纳方自治。映射可以只消费能力的一部分；
  **未完整消费不是契约缺陷**，不得据此回退契约能力。消费侧仅可使用已登记且不承载产品语义的渲染/传输机制常量；契约布局参数缺失或非法必须显式停机，不得补默认值或夹取范围。
- 两个方向都禁止：在契约内引入与已声明方言竞争的第二布局方言；采纳方用布局 facet 推断或发明业务语义。
- 若某个已声明 facet 在应用层没有消费者，按 §14.2 记为应用层消费缺口；处理方式是在应用层补齐消费，
  或在应用层显式声明不消费，**不是删除契约声明**。不消费登记不能豁免当前页面已经生效的布局约束；
  能力集合可大于采纳范围，但当前页面选择的能力必须有受支持映射，否则发布／消费显式报缺口。
- 该界限由 `scripts/verify/unified_page_contract_v2_assembler_guard.py`（声明能力下限，fail-closed，含自检负例）
  与 `scripts/verify/unified_page_contract_v2_client_guard.py`（唯一网格方言）共同固定；
  决策记录见 `.agent/decisions/layout-contract-ownership.yaml`（ARCH-DECISION-003）。

### 14.4 低代码布局可配置范围（2026-10-13，强制）

低代码编辑的是后端认可的逻辑布局声明，不是独立页面实现。以下是目标职责规范，不能仅凭本文宣称
设计器、发布校验或所有渲染器已经实现。实现缺口须进入原批次台账并用实际行为闭合。

| 内容 | 声明与执行边界 |
| --- | --- |
| 结构 | 可配置已授权字段的分组、顺序、页签及已登记区域；每个字段出现位置有稳定节点身份与父节点。同字段多次出现不能只按字段名合并 |
| 逻辑尺寸 | 可配置合法容器列数与 24 单位跨度；明确跨度所属父容器、作用对象及映射。`columns` 规定容器网格，`span` 规定节点占用，不能将两个值当成竞争默认值 |
| 呈现选项 | 仅选择 P0 登记、对应字段类型及目标渲染器支持的组件／展示参数；不接受任意 DOM、CSS、脚本或组件内部实现属性 |
| 权限 | 可在授权范围内收紧显隐、只读与可办；不得扩大字段、记录、动作权限，不得改写服务端业务约束。角色不选择分组、顺序、列数或跨度 |
| 视觉机制 | 官方组件及通用适配层负责断点、间距、对齐、焦点与交互。映射须登记且不改变声明的业务结构，不按角色或可见字段数重构布局 |

P0 定义能力白名单、类型／取值范围、节点身份、来源合成及冲突规则；P1 定义行业默认，P2 定义客户确认配置，
P3 承载授权管理员的草稿、预览与发布。谁有权编辑配置，与发布配置作用于哪个入口／视图／公司是两个维度；
发布者或浏览者的角色不能自动成为布局选择条件。设计器编辑源配置，不能回写运行时契约作为第二事实源。

后端输出单一最终布局及其结构来源、配置版本，另行输出权限结果；设计器还需消费受授权的可配置能力说明。
源配置允许省略的属性由声明层按已登记规则解析，最终消费者必需的属性必须显式给出。
缺失、非法、互相矛盾或目标采纳方不支持的生效声明必须拒绝发布或进入契约缺口状态，不能静默丢弃、夹取或回退。
原生节点与投影 widget 的跨度若不同，必须证明属于不同容器坐标及明确转换；同一节点同一坐标不得有两套值。

权限裁剪可使被隐藏内容不占视觉空间，但不得重新分组、排序或重新计算剩余字段的业务跨度；
不为了保留布局发送无权字段的值或敏感元数据。精确像素相等不是跨角色不变量，结构归属和宽度规则才是。

验收分三段：后端证明合法配置可合成、非法配置被拒绝且权限不被放宽；契约证明节点、来源、尺寸与权限无矛盾；
前端用确定契约证明官方组件实际执行。需覆盖一次合法低代码布局变更、同入口跨角色权限裁剪、缺失／非法参数停机及
不支持能力拒绝，不能以 schema、选择器或样式字符串存在代替上述行为。

## 15. 客户端动作边界（强制）

`ir.actions.client` 属于 Odoo 原生 Web Client 的客户端扩展机制，不属于契约驱动产品前端的页面主线。

硬约束：

- 产品导航不得为 `ir.actions.client` 签发 route authority；
- 产品页面不得按 client action tag、params 或 XML ID 选择业务组件；
- 产品工作台必须使用模型化 `ir.actions.act_window`、正式 scene 或其他已治理的契约入口；
- 自定义集合展示必须由原生 tree/search/form 与模型字段生成基础契约，再由后端输出明确 presentation；
- 前端只能按 presentation 语义选择通用渲染器，禁止读取模型名、action tag 或中文菜单名推断页面类型；
- `ir.actions.client` 可以继续服务 Odoo 原生后台，但不能经菜单投影或动作适配被提升为产品页面。

一句话口径：客户端动作留在 Odoo，产品运行时只承接后端已经合成并授权的正式页面契约。

## 16. 集合页面渲染器注册边界（强制）

列表、卡片、流程看板、层级浏览、透视、图表、日历、甘特、活动和仪表板必须统一经过 `Action Surface Renderer Registry`。`ActionView` 只负责通用页面运行时与宿主，不得直接按专用语义选择组件。

复杂视图尚未实现时也必须先登记正式 renderer key、当前 fallback、能力状态和稳定原因码；禁止以散落的 `v-if`、模型名、菜单名或自定义页面静默替代。未知语义失败关闭。详细规范见 `docs/architecture/action_surface_renderer_registry_v1.md`。

## 运行时结构权威补充（2026-09-16）

原生视图是默认基线，不是唯一可定义布局的来源。授权行业默认、客户偏好与管理员配置由后端按统一顺序合成，校验业务和安全约束后输出唯一有效树。本文“不得重写原生结构”约束前端擅自解释及重复默认路径，不禁止合法低代码结构配置。正文、导航、预览共同消费最终树。完整冲突、身份、发布和回滚规则见 `native_first_form_structure_authority_v1.md`。

### 本轮布局坐标机制登记
等分字段网格列数必须为 24 的正整数因子（1/2/3/4/6/8/12/24），不得取整；原生缺省列数由 P0 声明为 2，显式非法或冲突不回退。同 occurrence 的 native node.span 与 widget.span 使用同一父网格坐标。已声明 field 节点的独立宿主在父网格占位后，内部控件使用 singleton 映射 columns=1/span=24 填满该 cell；分组内批量字段继续消费各自声明跨度。此映射由 layoutSpan.containedFieldLayout 登记，不依据可见字段数量或角色，不覆盖业务跨度。只读窄屏单列属于既有响应式映射，先验证原声明，再执行折叠。
