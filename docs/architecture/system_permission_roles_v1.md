状态：F01–F05 已形成未发布的本地候选与定向证据；整体仍 verification_pending。下文完整角色注册/发布契约仍是后续设计，不能视为已实现。

## 已确认的边界

系统角色承载权限；岗位与任职由用户定义，不能授予系统权限。岗位变化不得自动写角色分配或授权组。项目成员与公司范围是单独的数据授权关系；拥有办理对象或岗位不产生操作授权。后端始终执行 ACL、记录规则、受控数据范围及业务动作约束。前端只消费契约。

角色定义、显式分配与有效组闭包必须区分。role_surface.role_code 是现有呈现兼容字段，不应升级为全部权限的唯一依据。多个权限角色不能被首页主角色吞并。

## 责任归属

P0 smart_core：通用角色注册/发布/分配、委派边界、授权投影、审计、版本与失效。
P1 smart_construction_core：施工行业标准权限角色及能力定义。沿用现有 role_catalog 消费入口，禁止新增并行身份权威。
P2 仓外客户模块：确认的长期客户权限配置。P3：租户运行时角色草稿与发布。P4：迁移与验证。
角色实例与用户分配属于租户库，不集中到平台库；平台管理员不自动取得租户权限。

## 目标契约

以下为待实现接口语义，不代表已经创建模型。

- permission_role：不可变 role_id、命名空间内唯一 code、中文 label、source_owner、source_kind、lifecycle、active_revision_id。
- role_revision：role_id、revision、capability_keys、授权组绑定、data_scope_policy_refs、delegation_policy_ref、content_digest、发布人/时间。
- role_assignment：user_id、role_id、state、assignment_source、授予/撤销人及时间。明确分配不能从 groups_id 逆推。
- effective_authority：role_ids、各角色有效版本、授权版本、能力与来源说明、数据范围引用。服务端生成，客户端提交不能覆盖。
- presentation：landing_scene_candidates、显示策略等独立于授权；workspace.home 如被采用须显式声明。

res.groups 作为 Odoo 授权载体继续保留，不复制 ACL。保持现有组/XMLID，禁止按名称推导权限。能力键不能直接等同任意组；委派检查完整继承闭包，不只检查直接包含组。

角色发布流程：草稿→校验及影响预览→版本冲突检查→事务内发布有效版本与组投影/授权版本→提交后清理缓存。失败不得局部生效。撤权后的新请求须重新校验；已开始的敏感写入在实际提交动作前须按该操作的授权事务设计处理，不能声称 token 失效可撤销已提交交易。

角色发布、分配和权限定义变化均进入失效依赖；仅比较组XMLID集合不足以作为未来动态角色的完整失效依据。角色版本/用户授权版本的具体存储和批量失效策略在AUTH-03以非零并发/撤权测试确定。

## 维护权限

查看、分配、编辑、发布、特权角色管理分别声明。使用权限不等于授予权限。租户管理员仅可操作被委派范围及允许的目标用户；禁止通过修改已分配给自己的角色间接扩权。普通业务配置权限不自动包含权限管理权。

内置定义由产品版本维护，租户通过派生定义表达差异。角色停用第一版要求无有效分配；删除优先归档，保留历史证据。组合限制在服务端检查；多个角色的记录范围遵循实际 Odoo 规则组合，不擅自以简单并集或交集替换。

## 迁移与兼容

先只读建立旧权限闭包、显式/继承来源未知项与代表操作基线。未知直接组授权不得自动删除，也不得伪装成用户显式授权。对每项给出保留为技术基础、映射角色、历史例外或需修复的结论。

投影影子比较通过后再切换单一权威。切换后旧入口转为同一分配服务，不能双写两套角色口径。服务账号、安装初始化与受管维护单独登记技术授权，不借技术组获得未声明业务权限。

恢复包括旧有效定义、分配记录和授权投影；恢复旧版本前重新评估已撤销权限，避免盲目重新授权。安装/升级不覆盖租户角色与客户扩展。

## 必测不变量

1. 仅改变岗位，角色与操作授权不变。
2. 仅改变角色，不改变岗位事实。
3. 撤销一个角色保留其他角色提供的重叠权限；撤销最后来源后权限消失。
4. 同一组身份下改变权限定义，旧缓存/会话不能继续执行被撤销操作。
5. 无XMLID运行期角色具有稳定身份；不同命名空间不能重放。
6. 无角色不会由能力模块兜底成owner；登录的基本技术权限与业务授权分开。
7. 真实system.init最终导航和操作权限一致；手工构造role_code不构成验收。
8. 非授权组组合、间接特权继承、跨公司/租户分配均被服务端拒绝。

## AUTH-01 已验证的迁移约束

2026-10-19受管local.dev事务测试确认：仅由角色继承能力与另外直接授予相同能力，在Odoo groups_id中得到相同集合。禁止用集合差集恢复显式授权来源。旧的“保留所有非可分配组再替换角色”会留下被撤销角色的权限，已用真实客商黑名单动作复现；不能作为新分配服务的兼容实现。

后续有效组投影必须从有来源的有效分配重建。历史未知来源必须显式显示未归因/待处理，既不自动撤销，也不能将这类撤权报告为已完成。具体错误与影响预览契约在来源模型实施时声明，客户端不自行判断残留权限。

## F02 最小实现载体（候选，未发布）

P0 res.users.sc_group_authority_state 为服务端只读来源快照：version/status/revision/actor_uid，以及已确认时的roots与observed。roots只取明确提交的原生组命令，不从有效组反推；这是native组分配的来源机制，不引入第二份角色目录。角色定义与发布版本的完整产品模型仍按后续批次推进。

P1现有两个角色字段沿用；修改时先锁定用户行并验证来源快照与有效闭包，重新组合“剩余显式组根 + 请求角色 + 已声明技术基础”，由Odoo投影implied组。增量命令以当前显式角色为起点。直接授予的能力根不会随角色撤销而丢失。

历史未知、反向users写、定义变化或投影漂移时拒绝角色修改，错误码GROUP_AUTHORITY_ORIGIN_UNRESOLVED/PROJECTION_DRIFT；数据库保持原授权，不宣布撤权完成。原生明确全量groups_id替换可以建立新的明确来源，但业务配置入口不得借此绕过未知来源检查。客户端不能直接写快照字段，没有context布尔开关可跳过。反向组成员维护和原生reified组字段不能伪造已确认来源。


### F01 审批人员兼容入口（候选）

`sc.approval.scope.user_ids`是审批执行组的只读授权结果，不是第二套人员授予来源。所属P1声明readonly及维护说明；原有人员inverse、打开新增向导和向导执行方法保留为明确拒绝，旧客户端无法借此写入组或新建账号。实际系统角色维护入口保持，角色授予/撤销后该投影同步变化。既有scope_key、policy执行组映射、历史组成员不由本修复迁移。历史来源未确认仍须另行对账，不能因显示在审批人员中就推定其来源已确认。


### 显式来源确认（本地候选已验证）

P0原生系统管理员用户表单提供“核对并确认授权来源”与“查看来源确认记录”。不自动给根组预选值；管理员必须选择从现在起作为直接来源的根组，并填写依据。根组可包含需要独立保留的能力，因此界面明确提醒该选择会影响日后撤权。确认不声称恢复历史，不变更groups_id，根闭包必须等于当前有效权限。

`sc.group.authority.reconcile`保存服务端预览状态，禁止客户端改写目标、预览、观测组和完成标记；提交锁定向导和目标用户，重验操作者权限及组、定义、来源修订、公司/启用状态。发生漂移或重复提交即拒绝。`sc.group.authority.confirmation`保存不可公开增改删的确认审计；ACL只允许系统管理员读取。原生业务配置管理员无此确认权限。有效来源确认后，原P1角色维护可以继续，独立授权按明确根组保留。

这些是机制与合成事务验收；现有真实账号仍需管理员依据有效资料逐项确认，不允许批量从有效组推断来源。事务内漂移反例不是多事务并发压力证明，原生get_view不是前端HTTP完整旅程证明。


### 已验证的撤权传输边界

受管local.dev事务中，使用现有签名配置与既有smoke命名空间夹具，通过真实密码登录取得JWT：撤销角色后旧token在system.init收到401/AUTH_REQUIRED，重新登录取得的新token正常认证。原生浏览器会话先完成客商列黑/解除，撤角色后同一会话的再次列黑请求被拒绝，业务对象保持未列黑。测试路由及合成数据回滚，配置回读一致。本结果不替代远端角色全业务旅程，也不构成跨独立数据库事务的并发证明。


### F03 令牌版本维护边界（候选）

令牌版本递增由P0私有方法`res.users._sc_bump_token_epoch`负责，锁定用户行后读取并递增。公开write拒绝显式token_version（TOKEN_EPOCH_SERVER_OWNED）；安全字段写入不接受sc_skip_token_epoch_bump客户端context跳过。logout复用同一私有方法，不通过公开write写版本。此方法的调用权威是服务端代码，不是客户端布尔开关；行锁实现尚不构成真实多事务并发验收。无schema变更。


### F04 原生组入口的失效传播（候选）

`res.groups.write(users/implied_ids)`对写入前后的成员并集同时使来源未确认并递增令牌版本，包括移出的成员；原生用户表单`in_group_`和`sel_groups_`字段也触发安全版本递增。这里使旧认证失效，不从反向成员关系推断直接授权，不改变原生继承组的增删语义。组create/unlink与真正并发的完整证据仍需后续审计，不将write覆盖外推为全部生命周期通过。


### F05 组生命周期（候选）

组create附带users已通过原生内部write触发来源及令牌失效；原生fields_get声明的sel_groups降级已验证。组unlink在原生删除成功后，对删除前的现存成员标记GROUP_AUTHORITY_GROUP_DELETED并递增epoch；无关用户不失效，权限拒绝删除不改变来源或版本。新增单组/批量/拒绝用例仅覆盖事务内行为，真实多事务结论仍未取得。


### 真实多事务验证（已完成的具体范围）

经所有者授权，在新建受管sc_contract_lifecycle技术隔离库，三个并发场景已通过：同一向导重复确认、同一用户两个向导确认、同一用户epoch并发递增。线程各自持有独立连接/事务并在屏障前读取快照；确认仅一个提交且审计唯一，败者新事务重试拒绝；epoch冲突按测试约定重试后净增2。原始事务身份、源码hash和提交后回读见run.real_concurrency。该结果取代前文对这三个场景的“尚未验证”历史描述，不代表任意负载或跨进程部署压力保证。证据保存后已受管回收所有隔离卷，非产品部署、非真实账号来源迁移。

### F07 业务配置管理员的委派边界（候选）

P1用户维护安全过滤不再由客户端sc_runtime_user_management开关决定；非sudo的业务配置管理员（不含原生系统管理员）即使省略上下文也必须过滤。sc_runtime_user_management_sudo只在服务端env.su同时成立时用于内部递归，客户端标记不能授予权限。公司访问范围只接受已有公司关系的3/4/5/6命令并验证最终集合；拒绝通过0/1/2对关联公司执行对象增删改。原生自身用户偏好仅在所有字段属于服务端SELF_WRITEABLE_FIELDS时保留原生super校验，不新增sudo。
这修复独立开发审计发现的既有上下文提权/公司对象写入旁路；不修改系统管理员原生授权、不推断历史来源、不作为完整角色产品化或最终独立交付审查结论。精确反例、修复及兼容结果记录在同一run。


### F08 委派创建的默认上下文边界（候选）

客户端default_*与显式vals同属不可信输入。P1用户委派写入在sudo前通过私有_sc_runtime_user_sudo_context清除此类上下文，防止ORM默认值补回被safe_vals排除的partner_id或sc_project_member_assignment_ids。create及write中的嵌套创建沿用同一边界。需要的初始密码先由原调用环境校验并显式放入safe_vals；既有sc_default_initial_password、语言及公司上下文保持，返回记录恢复原调用环境。原生系统管理员非委派路径不受此过滤影响。


### F09 委派操作不能绕过原生用户规则（候选）

公司范围与非特权身份筛选只是P1委派约束，不能替代原调用者对res.users的ACL及记录规则。委派write在sudo前检查原环境write ACL及目标record rules；委派create先检查create ACL，随后在内部保存点创建并恢复原环境检查create规则，拒绝时回滚该次用户与关联记录。返回记录保持调用者环境；自助字段路径继续由原生super执行权限校验。


### F10 人员部门/岗位关联边界（候选）

P1委派用户创建/修改中，sc_personnel_department_id与sc_personnel_job_id必须在原调用环境验证关联存在、read ACL及record rule；关联公司非空时必须等于请求处理后的用户公司。验证通过后方可sudo执行人员档案inverse，避免跨公司或隐藏ID关联。False清空和原生无公司共享载体保持既有语义，不在P0添加行业字段规则。


### F11 公开建立人员档案动作（候选）

action_sc_ensure_employee_profile在创建任何员工前，用原调用环境对整批用户检查write ACL/record rule、维护角色与公司范围。普通业务配置管理员还须通过既有非特权可维护目标过滤；原生系统管理员与sudo保持原有维护边界。校验完成后调用既有helper，重复调用继续返回既有档案。该修改不影响私有inverse；default_job_id探针未复现问题，不列为已修复漏洞。
