# SCE 能力授权模型 v1（CAP-01 通用验收规范）

状态：设计冻结，适用于所有工作场景与产品交付

## 1. 四层权限架构

| 层 | 名称 | 回答的问题 | 权威 |
|---|---|---|---|
| L1 | 业务角色 Role | 用户在企业承担什么工作职责 | 角色目录（仅身份标识） |
| L2 | 能力授权 Capability Authorization | 用户被配置了哪些系统能力 | 能力模型 + 能力组 + 角色-能力配置 |
| L3 | 资源与数据授权 | 用户能对哪些资源执行什么操作 | Odoo ACL + Record Rules + 公司/数据范围 |
| L4 | 执行判定 | 当前用户能否执行这一次操作 | 服务端最终授权 |

角色可以关联多个系统能力，多个角色可以共享同一种能力，但角色名称本身不授予任何权限。

## 2. 两条独立治理链

```text
能力资格链：发现 -> 识别 -> 契约化 -> 验证(preview/standard) -> 发布
  （证明系统具备某项功能的质量）

用户能力授权链：角色 -> 能力配置 -> ACL/Record Rules -> 服务端执行判定
  （证明用户能否使用它）
```

两者独立。能力资格证明“系统有此功能”，用户授权证明“该用户可用此功能”。

## 3. 三项授权检查（C1 及所有写入/读取能力通用）

1. `capability_entitlement`：系统能力模型是否允许执行。
2. `native_resource_authorization`：Odoo ACL、Record Rules、公司/数据范围是否允许。
3. `execution_authorization`：真实服务端请求是否通过全部授权。

必须证明三个环节共同成立。能力授权不能替代原生授权，拥有能力不等于绕过 ACL 或 Record Rules。

## 4. 测试场景定义规则

- 测试主体可用业务角色标识（如 pm / general_user），但角色只用于识别测试主体，
  不是授权判据。
- 授权判据是 `capability_profile`（能力配置）+ 原生 ACL/Record Rules + 服务端结果。
- 不允许“角色名 → PERMISSION_DENIED”的直接推断。

四类标准场景：

1. 具备创建能力 → 允许（仍须通过 ACL + Record Rules）。
2. 只有读取能力 → 拒绝。
3. 无相关能力 → 拒绝。
4. 有能力但资源/数据范围不符 → 按服务端授权结果拒绝。
