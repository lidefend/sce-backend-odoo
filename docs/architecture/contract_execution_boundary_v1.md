## 1. 建议裁定

**契约是前端执行行为的声明依据，不是可以绕过后端检查的授权凭证。前端拥有受约束的本地解释执行权，后端拥有业务事实裁决与事务提交权。**

- 计算位置、数据事实来源、持久化位置、权限裁决、业务生效时间是不同维度，不能用“在线/离线”或单一 executor 字段全部替代。
- 前端可以执行已登记的通用交互机制与契约显式声明的纯计算；业务条件、规则、可见范围和可执行操作不得由前端按名称推断。
- 单一通道指所有服务端执行仍经现有 intent/handler 链。浏览器内返回、展开、格式化和输入暂存无需制造一次 HTTP 请求。
- 本地规则可以给出输入错误和交互反馈，不能证明最终业务可提交。后端重新校验受理时的用户、公司、项目、字段、状态、版本和业务规则。
- 不向浏览器下发任意 Python/JavaScript 或允许 eval。解释器只执行已登记、可界定输入和副作用的算子；无法解释的声明显式报契约缺口，不猜测、降级为更强执行或自动联网重放。
- 无新声明不自动获得新能力；现有受控在线路径继续按其原协议运行。本研究不要求为旧动作偷偷补默认 local/deferred 标签。

## 3. 操作类型与权力矩阵

local/local_deferred/server_read/server_command/hybrid 在本文仅为审计标签，不是拟立即新增的 Schema 枚举；分类对象是一个执行阶段，复合操作应拆阶段。

| 主要操作 | 浏览器获准阶段 | 服务端权威阶段 | 审计分类及限制 |
| --- | --- | --- | --- |
| 解码、布局、格式化、分页控件交互 | 按已支持契约渲染，局部表达和临时状态 | 提供有效契约和策略 | local；契约加载是独立的 server_read |
| 本地字段校验、规则表达式、派生展示 | 仅支持的算子、已知完整输入；未取到的值不能当零/空参与结论 | 约束、onchange、业务计算和保存再次验证 | local + hybrid；提示不冒充保存成功，不能模拟任意 ORM 方法 |
| 返回、展开、丢弃未提交输入 | 执行通用客户端命令 | 无业务撤销 | local；丢弃本地输入不是撤销已提交业务 |
| 场景/关系导航、弹窗 | 组织声明参数、打开容器 | 缺失契约、关联数据、最新权限在线获取 | local + server_read；不得凭本地可见性证明目标权限 |
| 排序/过滤已持有数据 | 只处理已合法获得且仍满足本地使用策略的数据 | 全量查询、总数、跨页搜索、敏感汇总由服务端提供 | local 或 server_read；必须声明数据集是否完整，不能把当前页过滤说成全台账结果 |
| 项目台账、状态、关联查询 | 展示明确标识时效的结果 | 身份、字段、公司/项目范围、Record Rules | server_read；未来本地快照读取须独立授权和新鲜度策略 |
| 新建字段暂存、恢复 | 按 intakeAutosave 白名单/身份/期限保存和恢复 | 提交时重新校验当前契约与权限 | 已有 local；恢复值不自动提交、不复制服务端默认值/状态 |
| 编辑、one2many、业务配置表单保存 | 组织变更、显示预期结果 | ORM 写入、关联校验、版本冲突、事务 | hybrid；record.save/“保存草稿”仍是服务端写入 |
| 导入、批量办理 | 选文件、预览可本地完成的格式错误、组织选中集合 | 原生导入/向导、逐项权限、业务执行、批次事务与回执 | hybrid/server_command；recordset 不隐含本地批量执行或离线资格 |
| 审批、付款、过账、角色授权变更 | 收集理由/参数、展示影响；审批中展示待审 | 当前权限、审批规则、状态迁移、实际提交 | server_command；无审批规则时仍由后端统一机制受理并执行 |
| 附件采集/上传/删除/下载 | 选取文件、预览，获准时暂存 | 记录绑定、存储、访问控制和下载许可 | 分阶段；持久离线采集尚需声明和存储机制，上传不能伪装成本地完成 |
| 导出、报告、打印 | 可打印获准的当前呈现 | 扩大数据范围的导出/报告、敏感读取须服务端核验 | 不能因 local 标签绕过专用导出能力 |
| 断网现场记录 | 只有显式准入场景可保存“待提交意图” | 恢复连接后重新校验、受理和生成真实业务记录 | local_deferred 是未来能力，现有 create 暂存不自动升级为它 |
| 刷新、错误重试 | UI 状态及已声明重试准备 | 重新读事实；写入重试先查受理结果/幂等事实 | 读写分开；网络超时是结果未知，不能认定未提交 |

入口可见性保持已有裁定：有读取权限应提供入口，空数据不等于无权限；没有任何可访问/办理能力则不投影入口。断网状态和无权限是两种原因，不用隐藏入口掩盖资产或联网缺口。远端撤权与离线界面无法即时一致时必须展示快照/待联网状态，不能承诺实时授权。

## 4. 五种分类需要的语义维度

先在现有 action/mutation/runtime/数据契约中逐项定位责任，再决定是否增加字段。不得把同一含义在三份契约各写一遍。

- 动作身份与效果：稳定 action/intent、executor、对象/recordset 范围、只读/暂存/业务写入副作用。
- 事实依赖：纯展示输入、来源投影、业务记录快照、动态状态、权限与公司/项目上下文。
- 本地使用条件：字段/附件白名单、是否允许持久保存、适用场景、期限、容量与失败处理；不是用户勾一个“离线”就全部启用。
- 有效性：来源配置/契约内容摘要、客户端解释器能力、数据版本、身份/权限 epoch、使用范围。内容身份用于拒绝陈旧执行，不等于恢复旧契约多版本兼容。
- 提交协议：当前授权重验、前置记录版本、幂等键作用域和保存期、响应丢失后的结果查询、最终回执与读取验证。
- 故障语义：不支持、契约缺口、需要联网、待提交、待审批、冲突、拒绝、结果未知分别表达；不能统一成成功或重试。

建议保留 executor 的“由谁执行”职责、executionScope 的“对哪些对象执行”职责，将本地持久化、时效和重放资格作为独立且可校验的策略维度。五分类可由声明事实形成工具审计投影，但浏览器不能靠命名或业务习惯自行生成授权。

### 4.1 契约解释器与业务操作运行器

通用解释器只执行**已登记、版本化、输入输出及副作用边界明确**的通用算子：解码、布局、格式化、输入校验、导航和交互状态。登记必须说明算子身份、解释器能力版本、输入类型/完整性、输出类型、允许副作用、确定性、资源预算和不支持时的行为。版本用于能力匹配及明确拒绝，不意味着恢复多版本业务契约兼容。

业务操作运行器负责参数准备、统一 intent 提交、消费权威回执和按声明刷新投影。它不能从页面布局、动作中文名、字段命名或已有数据推导业务规则。不能把任意业务脚本、任意网络访问、原生 ORM 方法或者权限求值器注册成“格式化算子”。

纯解释阶段输入齐备时可以零网络；需要新增事实的请求由业务操作运行器明确发起。调用回调的名称不足以证明无副作用，必须追到最终请求/写入位置。运行器现有回调注入保留，但审计必须记录效果而不只记录接口类型。

## 5. 本地资产与现有缓存规范的关系

必须显式协调 `docs/architecture/contract_runtime_cache_layers_v1.md`：该规范限制记录相关已装配契约复用，规定静态源投影与动态事实分离；不能直接用本草案推翻其守卫。

代码已经存在 ETag 新建契约分支，而旧缓存文档 L3 表格仍写 etag 禁存，至少存在文档/源码口径差异，须在专门缓存审计中确认后统一；本轮不据静态差异宣告运行缺陷。

建议的未来资产层次：

1. 静态定义/结构/字典：有来源、依赖清单、内容身份和解释器能力；可复用不等于离线包已经依赖完整。
2. 授权与运行投影：特定用户/公司/项目/场景下的快照，不是许可票据；限制时效与用途。
3. 业务数据快照：明确记录集完整性、字段范围、版本、新鲜度、存储准入；不得作为最终状态裁决。
4. 本地草稿/附件：用户尚未提交的输入，和服务端事实隔离保存；单独恢复、丢弃和保留规则。
5. 待提交意图与服务端回执：需要持久队列后才能启用；本地排队与服务端受理不可合并成一个状态。

用户、租户/数据库、公司（包括集团内部）、项目范围及会话身份必须参与隔离。切换/退出后不能让旧上下文数据继续被新上下文访问；具体是清除还是封存待原身份恢复，需要产品规则。离线期间无法立即获知撤权，也无法远程保证已复制数据被删除；敏感数据离线资格因此必须单独裁定，不能靠 TTL 宣称实时撤权。

前端无需自行实现原生 Record Rules。服务端负责限定下发范围；客户端只消费声明和快照标签，提交时后端重新执行原生强制边界。

### 5.1 运行资产完整性（Runtime Asset Integrity）

“本地存在 JSON”不是可运行条件。对**本次具体页面/操作**，必须同时证明：

- 页面结构与必需子节点完整；组件/渲染器存在且满足其接口版本；解释器支持所有必需算子和契约能力。
- 字典、配置、子契约、必要数据及关系依赖形成可追溯闭包，标明数据完整性和新鲜度；结构摘要通过不代表数据可用或权限仍有效。
- 资产来自可信发布来源，清单、内容摘要、发布身份和依赖版本相互一致；摘要只能证明内容一致，不能自行证明发布者可信。
- 用户、租户/数据库、公司及项目上下文适用，当前用途和本地保留期限有效；静态资产不嵌入可跨企业复用的权限裁决。
- 资产加载分为待获取、齐备、待在线事实、不支持、过期/损坏等明确状态；不能用一个 ready=true 掩盖某操作缺依赖。

仅缺在线关系数据时，可呈现已完整的静态界面并明确标记该关系操作需联网；缺页面必需结构/算子时阻止相应页面运行。可选区域只有契约明示可独立降级时才允许局部不可用。禁止展示可点击但依赖必然缺失的动作，并把故障误报成用户无权限。

企业预编译应优先生成静态定义及依赖清单，不预编译用户未来的权限、业务状态或审批裁决。完整性结论绑定具体资产集合、解释器和上下文，不以所有文件下载成功代替。

### 5.2 企业配置发布与客户端资产更新

以下是 E2 的目标协议，尚未证明现有实现全链可用；不在本轮增加接口、缓存或数据库：

1. 配置编辑与发布分离。后端以权威配置修订及依赖关系识别受影响契约；未发布/审批未通过的配置不成为运行资产。
2. 增量编译、严格验证依赖闭包及运行资产完整性，生成不可变内容身份和清单。失败不把半成品设为当前发布版本。
3. 发布新静态资产身份；下发变更范围/失效信息。客户端通知或轮询方式后续选定，不能假设现有通知等同于完整失效通道。
4. 客户端先获取并校验新资产，再原子激活一个依赖一致的集合；不混用新字段定义与旧参数模板。拉取中断不得冒充更新成功。
5. 分离静态资产失效、授权失效、业务数据变更。权限撤销/公司变化不等待静态包更新才在服务端生效；企业角色发布也不因此自动迁移已有用户的版本绑定。
6. 对未完成输入和待提交意图保存其来源契约身份、字段身份、用户/公司/项目、数据版本及必要上下文；更新资产不得覆盖或静默丢弃它们。
7. 对当前契约重新校验：字段仍存在、类型/约束有效、操作仍准入且当前权限允许时，可恢复到新解释上下文；字段删除、类型变化、动作移除、权限变化等要求明确差异与受控修正。不能后台猜测转换、静默提交或让旧契约继续授权执行。
8. 无法兼容的输入保留为不可执行的待处理草稿，按受约束保留规则恢复/丢弃。保留用户输入不等于为旧协议维护执行兼容；禁止恢复旧规则来强行完成队列。

上述“版本兼容检查”指**当前声明下的输入适用性检查**，不是开发期保留旧业务数据或双协议运行的决定。静态发布身份、记录并发版本、授权 epoch 和用户角色绑定版本不能混为同一个版本号。

## 6. 统一执行器与同步：后续设计约束

不另建权限引擎，不另开业务 HTTP 入口。复用现有 scene mutation、action runtime、intakeAutosave 和 intent/handler，先定义共同的准备/提交/结果接口，再决定最小改造。

未来延迟提交建议状态：本地输入 → 待提交 → 发送中 → 服务端已受理/待审批/已提交，或冲突/拒绝/结果未知。服务端已受理不等于审批通过，传输成功不等于业务成功。状态由权威回执推进。

- 点击取消/丢弃：尚未受理时只撤本地排队意图；已发送但回执丢失先核对结果，不能声称取消无影响；已提交业务的反向操作是另一项受控业务请求。
- 恢复连接：先验证当前身份与契约资格，再校验记录版本；不把旧身份下的排队操作自动转给新用户/公司。
- 幂等：按操作与身份范围绑定稳定请求身份和内容摘要；服务端证明事务与去重记录一致。超出幂等保留窗口不得盲重放。前端 Map 去重不能替代此证明。
- 冲突：不默认 last-write-wins；返回差异和当前事实，让用户受控修正/重提。独立操作之间的临时 ID、依赖顺序、附件绑定及批次部分失败均需设计。
- 高风险审批/财务执行默认在线服务端裁决；本地准备不等于离线授权。是否允许某业务意图延迟提交，由平台准入与企业受约束配置共同决定。

### 6.1 本地状态、传输状态与业务事实必须分离

这些不是所有业务共用的一条线性状态机。至少分为三个独立维度：本地输入/队列状态、请求受理/回执状态、服务端业务状态；审批与支付还可以有各自状态。字段名称和 wire 格式本轮不冻结。

| 对用户的事实 | 唯一依据 | 不能等同于 |
| --- | --- | --- |
| 本地已填写/已暂存 | 输入存在于声明允许的本地载体，持久化成功有本地结果 | Odoo 记录已保存 |
| 本地待提交 | 明确准入的意图已可靠排队（未来能力） | 后端已受理或审批中 |
| 发送中/结果未知 | 传输过程或未能取得权威回执 | 失败且可安全重试、取消成功 |
| 服务端已受理 | 服务器对该操作身份的受理回执 | 事务最终提交、审批通过 |
| 审批中/已审批 | 服务端审批实例及其权威结果 | 本地校验通过、已经付款 |
| 已付款 | 服务端付款执行事实及回读 | HTTP 200、审批已通过 |

不得以泛化 success 合并这些层次。UI 的成功文案必须指向明确完成的阶段；“本地已保存”不能呈现为“业务已提交”。无审批规则时由后端直接通过的路径仍需权威执行结果。审批中的取消仅取消尚未生效的申请；已生效设置的反向变化仍是另一次受控业务设置。

## 7. 分阶段专题与准入

| 阶段 | 产物 | 完成标准 | 本轮状态 |
| --- | --- | --- | --- |
| E1 执行权审计 | 每类操作的生产者→声明→消费者→副作用→回执矩阵 | 固定语义与事实权威，无未知动作被猜测执行；与已有缓存裁定冲突显式处理 | 本文完成主要类型源码盘点；逐入口与浏览器证据 NOT_VERIFIED |
| E2 静态运行资产与企业增量更新 | 完整性闭包、增量编译/发布、客户端原子更新、草稿适用性与失效恢复 | 缺失依赖、权限/公司切换、过期资产不会被当有效事实；先评估现有缓存，不先建新库 | NOT_STARTED |
| E3 执行器收敛 | 复用现有运行器的统一生命周期和可审计结果 | 已有 online/local 行为不退化，未知/不支持执行明确拒绝，单一 intent 通道保持 | NOT_STARTED |
| E4 离线同步 | 准入场景、持久队列、服务端幂等/冲突/回执协议 | 断网、崩溃、重复提交、响应丢失、撤权、公司切换、过期与部分失败均有真实链路证明 | NOT_STARTED |

E1 应以当前动作目录和真实调用点生成覆盖清单，不手写固定入口数量。完整性必须覆盖 form/action view、场景动作、关系弹窗、列表 recordset、导入向导、附件、配置和权限审批；本文不是已覆盖每个业务入口的声明。

每阶段验证的核心是：真实后端生产契约 → 严格解码 → 实际执行分支/请求数量/本地与服务端事实 → 权威回执。零请求的本地交互、必须请求的业务写入、过期资格拒绝、不同身份数据隔离都需要行为证据。不得只测字符串枚举，也不重测 Odoo 通用权限机制本身。

## 8. 建议本次冻结与留待后续的事项

建议本次确认：三种执行权；契约非授权票据；五分类仅作审计标签；复用既有运行器；本地输入与服务端保存分离；未知效果不执行；单一服务端通道；公司/项目隔离；先 E1 再 E2/E3/E4。

暂不冻结：新 Schema 字段名称、离线数据库选型、允许离线的业务/敏感字段清单、保留期限、自动重放策略、批次原子范围和冲突合并算法。以上需具体场景与证据后决定。

禁止以本草案授权：新离线功能、扩大缓存、动态执行代码、客户端复刻权限引擎、恢复契约旧版本兼容、绕过审批、合并/部署或重启已暂停 CI 计划。
