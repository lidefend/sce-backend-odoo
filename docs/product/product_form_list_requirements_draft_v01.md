## 行业标杆对比门槛

本专题把行业标杆对比作为页面契约输入，而不是上线后的视觉复盘。公开证据仅用于提炼能力模式，不用于宣称本产品已经达到竞品水平，也不对竞品作未经实操的评分。

官方公开资料反复出现的完整度模式包括：合同—变更—付款—结算全链条档案、预算/合同/实际成本对比、项目—财务—供应链—税务贯通、表单间来源关联、经营指标和数据资产沉淀。办理便捷性模式包括：来源数据带入、后续单据生成、移动审批、多角色移动应用、流程化办理、风险预警和字段/流程可配置。参考：[广联达施工企业成本管理](https://www.glodon.com/product/375)、[广联达施工企业案例](https://www.glodon.com/case/357.html)、[明源云工程项目管理](https://www.mingyuanyun.com/solutions/urban-development/project-management)、[明源云成本管理](https://www.mingyuanyun.com/products/project-construction-management/cost-control)、[金蝶建筑行业方案](https://www.kingdee.com/solutions/architecture0.html)、[用友 BIP 项目云](https://www.yonyou.com/subject/xmy?withYonyouMenu=&zixun=0)。

每张代表页面必须同时检查两组维度：

- 信息完整度：身份、生命周期、来源到结果、明细与合计、业务证据、管控基线、权限范围、报表口径。
- 办理便捷性：任务首屏、一次录入、后续单据生成、渐进披露、搜索批量、移动办理、异常恢复、跨单据导航。

采用 0—3 级证据尺度。六张代表页面在推广前，所有适用维度必须至少达到 2 级“契约完整且主路径可办理”；只有经过登录态浏览器和真实运行数据验证，才能标记 3 级。

## 架构边界

- Formal Product Layer：P1 施工行业产品事实为主，登记 P0 通用契约与渲染机制依赖。
- Layer Target：产品事实审计、原生视图映射和页面语义契约设计。
- Module：`docs/product`、`config` 与只读静态验证。
- Standard vs User-Specific：只定义标准产品候选；不写 P2 客户偏好，不生成 P3 租户配置。
- Why Here：页面设计必须先绑定菜单、Action、模型、原生视图、权限和状态事实。
- Why Not Elsewhere：行业字段和流程不进入 `smart_core` 或共享前端；未经确认的字段不进入低代码运行时。
- Blast Radius：不改变模型、菜单、Action、运行契约、数据库、依赖或前端组件。

## 四态定义

| 状态 | 含义 | 可否进入实现 |
| --- | --- | --- |
| `implemented` | 主线已有明确菜单或能力载体 | 仍需按页面契约验收后优化 |
| `contract_gap` | 模型或入口存在，但页面、状态、权限或来源类型契约不完整 | 先补契约，再做组件/页面 |
| `planned` | 缺少正式产品闭环 | 不进入普通页面开发 |
| `merge` | 与正式中心现有办理、台账或报表重复 | 合并到同一事实对象或只读投影 |

“已有菜单”只证明存在入口；不自动证明字段、必填、审批、导出、打印、删除和运行角色可用。

## 七类页面配方

| 配方 | 适用对象 | 核心契约 |
| --- | --- | --- |
| `dashboard` | 工作台、驾驶舱 | 指标定义、期间、筛选、下钻、更新时间 |
| `master_data` | 客户、供应商、人员、材料档案 | 身份、有效性、引用关系、归档权限 |
| `business_document` | 合同、付款、入库、发票 | 摘要、主体、本次办理、明细、关联、证据、流程 |
| `complex_workspace` | 往来、退款、对账 | 多事实对象、差异、处理动作、追溯链 |
| `ledger` | 合同/资金/发票台账 | 只读事实、来源、余额、期间、下钻 |
| `report` | 项目、成本、资金、税务报表 | 指标口径、维度、期间、合计、刷新时间 |
| `configuration` | 表单、字段、流程、权限 | 作用域、版本、发布、回滚、影响范围 |

复杂业务单据使用完整页面。弹窗只允许用于低风险、短字段主数据或辅助选择；移动端 390px 使用单列。只读详情展示业务摘要，而不是整页禁用输入框。

## 成本来源契约

劳务、材料、机械和分包成本不能全量强制关联合同。统一候选来源类型为：

1. `contract_execution`：合同内执行，强制关联合同。
2. `spot_purchase`：零星采购或零星用工。
3. `site_variation`：现场签证。
4. `provisional_pending_contract`：暂估或待补合同。
5. `adjustment_reversal`：调整或冲销。

前端只消费后端给出的来源类型、必填和只读结果，不自行推断。

## 与组件专题的交付顺序

1. 本专题矩阵和代表页面契约先合入。
2. 从届时最新主线新建组件底座分支。
3. 保持 `Sc*` 业务语义组件；任何第三方 UI 框架只能位于底层实现。
4. 基于组件分支建立六页面堆叠分支并联合验收。
5. 组件底座先合并，六页面随后整理合并。
6. 按十中心小批量推广，不一次重写 71 页。
7. 会计账务另立专题。

旧 `codex/tdesign-enterprise-ui-foundation-v1` 只作为候选代码来源，不直接合并；本专题不选择或新增 UI 依赖。
