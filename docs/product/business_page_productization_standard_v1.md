# Business Page Productization Standard v1

本文件沉淀 PC-01、PC-02 两轮已完成主线集成的业务页面产品化方法，作为后续付款申请、
结算单、采购合同等业务页面的统一交付基线。它是流程与边界标准，不是某个页面的截图或
一次性验收清单。

## 1. 证据基线

| 样板 | 产品目标 | 合并提交 |
| --- | --- | --- |
| PC-01 | 项目管理工作空间（project.project） | PR #781 · `c6880a1c` |
| PC-02 | 综合合同工作空间（sc.general.contract） | PR #786 · `4212b079` |
| P4 | candidate 隔离验收车道 | PR #785 · `9db2fd9ff` |

两轮共同验证：平台原生组件与契约机制可以承载专业业务页面；页面差异主要通过业务配置
表达；浏览器验收可以绑定真实模型、角色、数据和候选身份；产品配置与工程治理可以通过
统一发布流程集成。

P4 是支撑业务页面交付的工程基础设施，不属于业务页面产品本身；其合并事实用于证明验收
能力已经具备，不代表每个业务页面都需要重新建设 P4。

## 2. 核心原则

1. **跟随权威发布入口，而非模型存在性。** 数据库有模型、模型有菜单、菜单已发布、
   用户实际可达，是四件不同的事。产品化目标必须是权威导航中已发布的真实入口。
2. **责任层归属固定。** P0 平台机制、P1 行业标准、P2 客户偏好、P3 低代码运行时、
   P4 交付工具各司其职。页面产品化落在 P1/P2 的视图与配置，不得把业务语义塞进
   平台机制或前端特判。
3. **原生视图复用优先。** 本标准覆盖的 P1/P2 页面产品化，优先通过原生视图与既有
   契约能力实现，不以新增页面专属 Vue 组件作为默认方案。模型计算、ACL、record rule、
   审批逻辑和权威导航属于独立责任范围，未经单独审计与授权不得随页面重排一并修改。
4. **统一产品标准，不强制统一数据模型。** 页面共用一套身份带、金额层级、字段完整性
   和响应式标准；不同模型只保留业务方向导致的必要差异，且差异必须记录来源。

## 3. 字段映射规则

1. 每个展示职责绑定权威字段；同一业务概念在不同模型下必须重新核对字段、计算来源和
   数据口径，不得仅凭字段同名迁移。
2. 不新增、不伪造模型不存在的字段。例如 `sc.general.contract` 不存在
   `amount_final`、`settlement_balance`，界面不得自行计算或伪造。
3. `amount_total` 若同时承担原始含税金额与最终执行金额语境，必须通过层级与标签区分，
   避免用户误认为存在两笔独立金额。
4. 零值不等于“无变更”。`change_amount_total = 0` 应表达为“变更金额待接入”等真实状态，
   不得显示为“没有变更”。
5. 生命周期、单据状态、审批状态彼此独立表达，不因视觉相邻而合并成单一状态徽标。
6. 配置达标不等于字段齐全：每个展示字段必须有业务职责、展示优先级、权限边界和真实
   数据来源，缺一不可。
7. 每个展示字段除权威来源外，还应明确展示条件，包括适用模型、合同方向、记录状态和
   当前用户的字段访问权限。条件不成立时应使用合法隐藏或空态，不得以默认值替代业务事实。

## 4. 布局规则

1. 身份区遵循统一职责标准，按目标模型的真实字段映射。标准职责包括主标题、业务编号、
   业务方向、生命周期、审批状态、业务分类、相对方和关联对象。目标模型不存在的职责
   可以不展示，但必须记录其不适用依据，不得伪造字段或强行补齐。
2. 金额层级是业务语义结构，不要求每个模型都拥有独立的原始金额、变更金额、最终金额
   和余额字段。字段不足时应明确说明金额口径，不得通过前端计算制造新的权威金额。
   收入/支出按方向适配履约字段，不复制同一组字段了事。
3. 四视口 1440/1024/768/390 需满足：无横向溢出、核心字段可识别、主操作可达、关键
   状态不丢失；合理换行不作为缺陷。

## 5. 权限边界规则

1. 页面产品化不修改 ACL、record rule、审批逻辑。只读/可见/编辑语义来自既有字段状态
   和契约声明。
2. 菜单可见不等于记录可读，记录可读不等于字段可读；验收需分别确认。
3. 验收账号使用已有受管 fixture 角色，不为了通过验收临时扩大权限或发布导航。
4. 只读、可编辑、不可见和不可操作分别属于不同权限语义。不能以隐藏按钮代替后端授权，
   也不能以页面只读状态推断后端记录权限；验收角色必须是实际业务职责匹配的受管角色，
   而不是简单挑选权限最大的账号。

## 6. 模型感知的质量校准

1. 统一质量标准不等于统一字段数量。结构复杂度类阈值按目标模型真实结构标定；
   例如 `relation_roundtrip.min_counts` 对 `project.project` 与 `sc.general.contract`
   分别声明。
2. 未知模型必须失败关闭，不允许自动套用较低阈值。
3. 结构数量达标不等同于业务能力通过；关系往返成功率、控制台错误、拒绝请求等
   行为性断言独立存在。
4. 模型结构变化后，应重新评估受影响的结构阈值；不得仅沿用历史阈值，也不得因一次
   验收通过而永久冻结阈值。

## 7. 适用范围与例外机制

本标准适用于依赖平台原生视图与契约机制的业务页面产品化（P1/P2 视图与配置范围）。
不适用于 P0 平台机制变更、P3 低代码运行时承载、P4 交付工具实现或生产部署协助。

例外机制：

1. 结构复杂度类阈值（如 `relation_roundtrip` 的 `min_counts`）可按目标模型真实结构
   校准，但必须同时提供模型事实、评审依据和负向测试。
2. 例外只能调整“结构数量”类门槛，不得降低行为正确性门槛：关系往返成功率、拒绝请求、
   控制台错误、横向溢出等断言不得放宽。
3. 不得因为某个页面难以通过而直接降低质量标准；差异必须显式登记来源与理由。
4. 未知模型一律失败关闭，不允许自动套用较低阈值。

## 8. 验收门禁（分层状态机）

| 层 | 门禁 | 证明内容 |
| --- | --- | --- |
| L1 | 静态质量 | 字段完整性、金额映射、XML 良构、结构锁、diff 检查 |
| L2 | 定向测试 | 非零收集、影响面覆盖、视图结构与分类器单测 |
| L3 | candidate 身份 | served SHA、DB namespace UUID、前端 dist 摘要一致 |
| L4 | 真实运行时验收 | Presentation、List Surface、Relation Roundtrip |
| L5 | 集成与交付 | Quick、publish preflight、CI、独立复审、受保护合并 |

前层失败必须短路；受管运行时只在更早的静态与定向门禁通过后执行。
L4 按页面实际表面选择适用的验收套件；例如纯展示型页面可能不存在独立列表入口。不适用
必须有明确依据，不能因为难以验收就标记为不适用。

## 9. 证据绑定与结转

1. 运行时证据必须绑定实际候选 SHA、数据库 namespace UUID、前端 dist 摘要，而非仅
   检查配置声明。
2. 文档变化不重拍页面；测试工具变化只失效依赖该工具的断言；跨提交复用必须记录
   确定性影响分析，不能只凭提交说明继承证据。
3. 两套方向或两个模型必须分别取证，不能用一个方向的结果推断另一个方向通过。
4. 证据结转必须以输入指纹和确定性影响分析为依据；仅有候选 SHA 的祖先关系，不足以
   证明证据仍然有效。

## 10. NOT_VERIFIED 纪律

未接线的业务语义保持 NOT_VERIFIED，不因 PR 合并、CI 全绿或页面能打开而自动获得结论。
不得为了通过验收伪造业务数据或把未验证语义包装成产品功能。

当前冻结示例：变更金额汇总关系、结算金额与最终合同价的关系、历史付款与新系统付款边界。

## 11. 完成状态分离

批次验收完成、主线集成完成、部署完成、用户验收完成是四个独立状态。PR 合并只代表主线
集成完成，不能推断部署完成或用户验收完成。

## 12. 新页面复用路径

1. 先判断目标页面是否已被既有产品化标准覆盖，优先复用既有配置与验收目标，不重复创建
   同类机制。
2. 确认权威发布入口（菜单/动作/模型/视图）。
3. 只读审计模型字段、计算链、关系与权限。
4. 按本标准完成身份带与业务分组配置，走静态质量门禁。
5. 用 candidate 车道绑定真实模型与记录完成 presentation/list/relation 验收。
6. 登记证据、Quick、publish preflight、CI、独立复审、受保护合并。

## 13. 标准版本与变更治理

1. v1 是基于 PC-01、PC-02 已合并成果形成的基线。
2. 后续业务页面实施可以发现标准缺口，但不能直接修改已冻结标准以迁就单个页面。
3. 需要修改标准时，提供实际案例、影响范围和兼容性分析。
4. 通过独立评审后升级标准版本。
5. 旧页面是否需要重新验收，应根据变更影响决定，不做无差别全量回归。
