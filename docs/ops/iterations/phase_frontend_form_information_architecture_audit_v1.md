# 前端表单信息架构专项审计 v1

## 1. 审计结论

当前表单体系已经具备较强的契约生成、统一渲染、响应式布局、状态操作和配置能力，但尚未形成成熟的“业务单据呈现体系”。问题不在于缺少章节，而在于现有验收主要证明结构完整，未证明信息是否围绕当前办理任务、普通用户是否只看到业务事实、只读页面是否按阅读逻辑呈现、附件与长文本是否按证据关系组织。

本轮权威判定：

- 技术结构成熟度：`8.2/10`。
- 业务信息架构成熟度：`4.7/10`。
- 正式产品表单基线：`暂不通过`。
- 允许继续复用的基础：统一页面契约、字段元数据、状态/动作、响应式容器、设计令牌、附件和协作能力。
- 必须专项升级的部分：普通用户表面过滤、办理主题摘要、只读投影、章节语义、附件/长文本编排、角色与模式差异。

该结论不否定已有前端建设。现有技术底座可以继续使用，不需要重新开发第二套表单；应在契约和渲染器上增加产品语义。

## 2. 产品边界

| 层级 | 本专题归属 | 不应承载 |
|---|---|---|
| P0 平台层 | 表单语义协议、create/edit/readonly 投影、字段角色、受众、空值策略、系统字段默认过滤、通用只读渲染器 | 建筑行业具体字段顺序 |
| P1 行业产品层 | 合同、结算、付款、报销、发票、项目等标准章节和首屏字段配方 | 单一客户偏好 |
| P2 客户产品层 | 客户确认的字段隐藏、排序、标签和角色简化 | 反向修改全局标准 |
| P3 运行时配置层 | 版本化的租户级表单覆盖 | 无审计的永久产品默认 |
| P4 运维/迁移层 | 来源、迁移、重放和核验证据 | 普通用户办理页面 |

## 4. 根因判定

### P0-1 普通用户表面缺少失败关闭的字段边界

当前产品化契约把 `legacy_*`、`carrier_*`、`create_uid/create_date/write_uid/write_date`、`active` 以及部分审核辅助字段声明为可见字段，并放入普通章节。即使章节名叫“来源追溯”，它仍属于普通表单 DOM 和章节导航。

根因是契约只有字段顺序、只读和可见性，没有可靠表达：

- 字段角色：业务事实、工作流事实、证据、协作、系统、迁移审计。
- 目标受众：办理人、审核人、财务、管理员、审计员。
- 目标表面：摘要、正文、证据、内部审计抽屉。
- 模式可见性：创建、编辑、只读。

### P0-2 只读态是“不可编辑表单”，不是“业务单据”

`ContractFormNativeCanvas.vue` 在只读模式下继续消费同一套 `layoutNodes`；`FormSection.vue` 逐字段保留标签和空值槽位。`render_profile` 主要改变可编辑性，没有生成只读专用的信息层级。

结果是：

- 空值与有效值获得近似权重。
- 标题、编号、对象、金额、日期等关键事实没有组成摘要头。
- 明细、附件、说明和审批历史仍按编辑字段序列出现。
- 用户需要阅读数据库字段，而不是阅读一张业务单据。

### P0-3 办理入口语义没有成为首屏权威

同一模型虽然通过 action 区分业务入口，但大量表单仍以“办理主信息”“基本信息”开篇，并在首组优先展示状态、校验、方向、来源等通用元数据。入口标题存在，却没有继续约束首屏的字段选择和摘要句法。

### P1-1 章节数量和语义粒度失控

章节导航达到 13–16 项时，已经从定位辅助变成第二套菜单。章节同时混用“系统信息”“办理类型”“项目与合同”“金额与日期”“来源追溯”等不同抽象层级，缺少稳定的领域配方。

### P1-2 附件与长文本未形成证据体系

65 个表单把 `note/remark/description/reason` 与 `attachment_ids` 放入同一个“说明与附件”区。两者交互不同：长文本用于解释，附件用于证明、预览、分类和核验，不能只作为相邻字段处理。

### P1-3 现有门禁偏向技术可用性

现有验收对创建、编辑、保存、关系选择、响应式和结构存在性覆盖较强，但缺少以下产品断言：

- 普通角色技术字段为 0。
- 普通角色来源追溯章节为 0。
- 首屏字段与办理主题相关。
- 只读空值默认折叠。
- 附件为独立证据区。
- 章节数量和认知负担受预算约束。

## 5. 目标表单体系

### 5.1 创建/编辑模式

1. 办理主题与状态：入口名称、单据号、状态、下一步。
2. 办理对象：项目、合同、往来单位、申请人等。
3. 关键事实：金额、税额、数量、日期、期限。
4. 业务明细：清单、结算行、发票行、材料或人员明细。
5. 办理说明：原因、用途、备注和其他长文本。
6. 附件证据：按合同、发票、凭证、审批材料、现场照片等分类。
7. 审批协作：意见、流程、活动和消息。

### 5.2 只读模式

1. 单据摘要头：标题、编号、状态、核心对象、核心金额和日期。
2. 关键业务事实：只显示有值或必须解释的字段。
3. 明细与关联单据：采用表格、卡片或摘要列表。
4. 附件证据：优先支持预览、下载、分类和缺失提示。
5. 办理说明：长文本按段落阅读，不保持输入控件外观。
6. 审批与时间线：展示决定、责任人和时间。
7. 系统/迁移信息：普通角色不渲染；仅授权审计/管理员从独立入口查看。

### 5.3 建议契约能力

在现有统一页面契约上增量扩展，不建立第二套页面协议：

- `sectionKind`: `summary | facts | details | narrative | evidence | workflow | audit`。
- `fieldRole`: `identity | context | decision | detail | narrative | evidence | workflow | system`。
- `audience`: 允许的标准角色集合。
- `renderProfiles`: `create | edit | readonly`。
- `emptyValuePolicy`: `show | hide | collapse_section`。
- `readPriority`: 只读摘要和正文排序权重。
- `attachmentCategory`: 证据分类和必需性。
- `surface`: `header | body | drawer | audit_only`。

前端只消费上述语义；不得按模型名、字段名或中文标题猜业务。

## 6. 专题迭代计划

### G0 基线冻结

- 固定本报告、77 个契约快照和 18 张浏览器截图。
- 把旧门禁定义为“结构完整性门禁”，不再称为表单产品质量门禁。

### G1 P0 契约升级

- 扩展表单语义协议和 Schema。
- 为未知 `fieldRole/audience/surface` 失败关闭。
- 普通用户默认排除 system、migration 和 audit-only 字段。
- 保留旧契约兼容适配器和 feature flag。

### G2 P0 只读投影

- 后端生成只读摘要和正文投影。
- 前端增加业务单据型只读渲染，不复制第二套业务页面。
- 空可选字段默认隐藏，必须解释的空值才显示。

### G3 P1 行业表单配方

首批按影响面处理：

1. 施工合同。
2. 支付申请。
3. 结算单。
4. 费用报销。
5. 进项/销项发票。
6. 项目详情。

每个模型先定义 P1 标准配方，再允许 P2/P3 覆盖。

### G4 证据与长文本

- 附件从通用字段组提升为 evidence section。
- 支持证据分类、数量、缺失状态、预览和下载。
- 长文本采用阅读/编辑双态，避免与附件共用同一布局语义。

### G5 全量迁移和门禁

- 逐批迁移 77 个产品发布契约。
- 建立普通办理人、审核人、财务、管理员、审计员矩阵。
- 覆盖 create/edit/readonly 和 1440/1280/1024/768/390 五视口。
- 保持旧契约回退开关，完成真实种子客户验证后再移除兼容层。

## 7. 完成标准

专题达标必须同时满足：

- 普通办理角色可见技术/迁移字段：`0`。
- 普通办理角色“来源追溯/系统信息”章节：`0`。
- 首屏摘要核心字段：`4–8` 个；首屏总业务字段不超过 `12` 个。
- 普通表单一级章节：建议 `4–7` 个；超过 7 个必须有领域理由。
- create/edit/readonly 三种模式有可验证的不同投影。
- 只读态可选空字段默认不占位；空章节自动折叠。
- 长文本与附件不再使用同一未分类字段组。
- 附件具备独立证据语义和分类。
- 390px 首个业务主题区可在首屏到达，无横向溢出。
- 权限、路由、接口和业务事实不因视觉重排发生漂移。
- 所有新断言接入正式前端发布门禁。

## 8. 总控建议

下一步不应继续逐页调 CSS，也不应让客户配置代替产品标准。先完成 G1 与 G2 的平台契约/只读投影，再用施工合同、支付申请和结算单做三个真实闭环。三个样板通过后批量迁移其余表单，最后开放 P2/P3 个性化覆盖。
