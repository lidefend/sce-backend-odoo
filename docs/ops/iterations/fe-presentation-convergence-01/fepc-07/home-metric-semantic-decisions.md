## 3. 兼容保留与旧版语义的硬边界

**保留兼容输出不等于认可旧指标语义。** 旧字段继续存在以避免破坏消费者，但不得据此宣称固定权重、默认颜色和阈值已成为正式业务规则：

1. 兼容输出继续存在，不新增首页消费。
2. 未批准的派生指标不作为正式业务决策依据。
3. 不因本轮治理主动删除字段、兼容handler或投影。
4. 若未来要停用，另行核查生产/脚本/测试/外部消费者、兼容期限与移除授权。

**不得追溯性重解释旧版disabled。** 不规定旧字符串必然等于“不计算”“不输出”或“一律不显示”，不因诊断与非空输出并存就认定当前首页故障。未来版本必须分别定义：

| 职责 | 必须回答的问题 | 本次未批准的内容 |
|---|---|---|
| 来源可用性 | 事实来源是否可用、是否位于授权范围，缺失原因是什么 | 不新增状态字段或枚举，不将旧字符串改成此维度的统一权威 |
| 计算结果有效性 | 是否得到符合已批准口径的有效结果；如何区分真实0、缺源、无权限、未计算、不适用 | 空值/缺字段/schema表示尚待版本设计 |
| 产品发布策略 | 已有值是否获准作为产品指标发布，哪些用途被允许 | 未批准的派生值不能凭有数值就发布为KPI |
| 目标受众展示策略 | 谁能在哪个页面看到哪种指标表达，消费哪个版本 | 不改变当前组件，不把diagnostics自动接成展示开关 |

业务等级level、呈现语义tone、生命周期progress需要各自的定义。没有定义时不能互相推导，不能由受限数量自动得出健康状态。未来若需要某种显式映射，应作为版本化定义独立评审，不能沿用默认映射就宣称已获本决议批准。

## 5. 后续实现准入条件

必须逐项满足，并由用户另行授权，方可进入实现：

1. **需求与负责人**：存在明确的真实消费者及用途；产品负责人指定指标业务负责人。指标治理不得因未决项存在而长期占据前端主线。
2. **定义与依据**：具有可追溯批准记录；统计对象、单位、时间范围、授权域、公式、限量/去重规则、状态规则及不适用行为均明确。正式化派生指数时单独批准权重与阈值。
3. **权限与上下文**：定义用户、租户/公司、业务范围及切换后的有效性；不扩大查询权限，不用前端试探所有路由证明可进入，不用sudo绕过当前账号范围。
4. **权威与版本**：服务端定义为语义权威；metrics、platform_metrics、metric block的重复载体明确来自同一批准定义及其版本。新旧字段优先级、发布/展示策略明确，不静默改变旧key的口径。
5. **兼容策略**：列出已有生产、脚本、测试和外部消费者，说明未知范围；明确旧版本保留方式、期限及停用条件。新增字段也要评估严格schema消费者，不把“只追加”视为天然兼容。
6. **可执行验收**：用例明确输入、授权上下文与预期输出/行为，覆盖合法0、来源不可用、权限不足、未批准、状态不适用及新旧版本；场景统计包含重复key、受限、预览和缺上下文；实际展示核对声明→消费→行为，不让前端自行算值或补语义。
7. **范围与回退**：按P0通用机制/治理统计、P1业务定义、前端消费划清责任；必要P3配置须另评估，不把业务规则落到P4；影响文件、回退和证据失效范围明确。
8. **授权记录**：以上条件通过评审后仍须取得独立实施授权；不得把本决议PR、CI通过或兼容保留当产品修复授权。

本轮没有执行这些未来验收，也没有修改指标名称、10/20权重、30/70阈值、颜色或展示行为；其他阈值、旧字段、handler和兼容投影亦保持原样。没有新增产品代码、运行时契约、配置或数据库变更。
